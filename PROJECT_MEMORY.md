# PROJECT_MEMORY.md

## Project purpose

HSK AI helps Uzbek-, Russian-, and Tajik-speaking learners study Chinese through structured HSK lessons, practice, AI assistance, and related tools. The course is the core product; AI, voice, XP, reminders, rewards, and subscriptions support it.

## Architecture

- `app/main.py` composes the FastAPI application; `app/bot/create_bot.py` creates the Aiogram bot and registers handlers.
- `app/static/` contains the Telegram Mini App and public web pages. Course content and browser-side flows live under `app/static/`.
- `android/` is the native Kotlin/Jetpack Compose client; `desktop/` is the Tauri client. Backend APIs own shared account, course-result, and entitlement behavior where implemented.
- Backend handlers and logic are divided among `app/api/`, `app/services/`, `app/repositories/`, and `app/bot/handlers/`.
- Standalone Admin PWA management APIs live under `app/admin_api/`. Its signed campaign commands create paused ad drafts and start one exact bounded round, create release-feedback/rating campaigns through the shared claimed outbound queue, and configure canonical discount offers through existing checkout policy. Delivery binds copy/revision/filter/audience (max 1000), shares two drainer slots and ten-recipient batches, and never activates the legacy scheduler or retries uncertain attempts. Optional existing promotion actions use shared localized defaults or explicit UZ/RU/TJ labels; the proof and private queue bind rendered markup/destinations, including contact-setting CAS, with no per-recipient contact lookup. Discount configuration defaults paused with legacy notifications off; native personal offers keep `target_user_id`. A separate signed one-round discount notice binds the current offer/canonical eligible audience/copy, atomically reserves `notification_sent_at` and uses the existing Android-first `discount_offer` delivery/Play silent-ack policy. Native-only users retain canonical ownership; current quota/repeat/payment reservations are checked by one bounded audience query. PWA notices cap native fanout at eight recent devices and release SQL before provider IO. Unknown FCM attempts get no automatic Telegram fallback deadline; known accepted native attempts keep the shared ten-minute acknowledgement fallback. Sending grants no access/payment state. Desktop-promo image replacement/removal uses exact passkey-bound JPEG/PNG/WebP content hashes (2 MiB/8M-pixel cap); existing course-ad raster replacement uses a separate exact passkey-bound command (1 MiB/8M-pixel cap). New course-ad creation supports one language or explicit UZ/RU/TJ copy, photo/video and validated type/placement/duration/link, defaults to paused and makes no AI calls; copy and media hashes bind the command. Course-ad video creation/replacement is an exact passkey-bound operation for one creative (25 MiB cap); it requires the verified proof before encoding, runs FFmpeg outside the DB transaction with one encode slot per worker, and attaches only the atomically published MP4 path in the revision-checked write. Both course-ad media operations use the existing volume and content-free audit, with no media BLOB or migration. Subscription checkout consumes Telegram QR `file_id`s; PWA QR replacement is a separate exact passkey-bound, 1 MiB raster operation for existing Alipay/WeChat subscription targets only. It leaves price/payment/access state unchanged and stores no image bytes in SQL. Preserve one-use WebAuthn proofs, hash-only audits and separation from statistics-only external MCP. Owned campaign photo/video uses migration 0131 metadata only: exact actor/session, 15-minute ready expiry, 20 uploads/hour, two IO slots and the shared single encoder. Photo is capped at 2 MiB/8M pixels; video at 25 MiB/4K/3 minutes, forced local container/protocols and bounded threads/time. Browser gets opaque ownership/hash metadata, never provider IDs. Ad drafts and release feedback bind the ready asset to their one-use command; captions including the release prompt must fit 1024 escaped UTF-16 units. Provider/encoder IO holds no DB connection; uncertain upload cannot authorize delivery. Bounded metadata retention preserves the one-hour quota window and never deletes referenced provider media. 0132 adds an indexed due time for ad/release jobs, at most 30 minutes ahead and strictly within the current session. The existing minute worker selects at most two due jobs into the shared drainer, with zero scheduler SQL when PWA is disabled. No session/private-body lifetime extension; early-send fences and fresh signed pending-only resume retain original due time/expiry. Long-lived unattended authority is not added.
- Persistence uses async SQLAlchemy models under `app/db/models/`; schema changes use `alembic/versions/`. Database settings and sessions live in `app/config.py` and `app/db/session.py`.
- AI provider calls are centralized in `app/services/ai_provider.py`; the current source uses Gemini first and OpenAI as fallback where supported. Feature services may set their own models and limits.

## Data model and business logic

- `users.id` is the canonical learner account key; unique `telegram_id` is optional and always a real Telegram identity. Subscription state includes `status`, `payment_status`, `start_date`, and `end_date`; there is no `subscription_until` column.
- `payments.user_id` owns manual Pro purchases by canonical account; optional `user_telegram_id` is transport metadata (migration `0106_canonical_payment_ownership`, including canonical subscription-entry backfill). Legacy integer callers still mean real Telegram IDs. The financial owner column has no cascading FK: purge clears the canonical association and retains approved facts under the existing anonymous negative financial grouping; nonapproved rows are deleted. Prices, review policy and 10/30/90-day paid terms remain unchanged.
- P3 local-first lesson translations remain a separately reviewed UZ/RU/TJ display-only catalog; keep all source Chinese, scoring, graded homework, Pro checks and canonical account ownership intact.
- Paid access requires approved payment state and an unexpired `end_date`. `app/services/subscription_service.py` owns paid-term activation and renewal; `app/services/user_access_state_service.py` distinguishes paid access from temporary trials and free/expired states.
- Checkout submit/reopen reports `provisional_access` for the particular pending Pro receipt as well as HSK 3.0 unlock. This reports the existing server-owned grant; it never consumes/replenishes a ticket. Pro review results return granted users to their original app section, while a spent-ticket review offers the configured admin contact.
- Temporary trial and referral benefits are not paid billing records. Keep their access predicates distinct from paid subscription checks.
- Manual subscription receipts have one reusable provisional Pro opportunity per user (`users.payment_preview_available`, `users.payment_preview_payment_id`, migration `0102_payment_review_preview`). It is consumed only after receipt submission, revoked on admin rejection, and restored on each *approved subscription payment* (not HSK 3.0 one-time unlock or manual Pro grant). It is temporary full content access, never paid revenue/status or a changed subscription term; Mini App and bot share the server-owned flag. A pending receipt gets a separate capped $0.50 AI budget until review, enforced for chat, image, Voice Practice and Live turns; do not override an existing paid/referral/7-day trial window. Temporary Pro receipt previews also grant HSK 3.0 track entry without treating the payment as approved. See `app/services/payment_review_preview_service.py` and `tests/test_payment_review_preview.py`.
- HSK 3.0 receipt rejection revokes provisional track access without deleting saved progress or cancelling independent paid/permanent grants. Mini App maps carry the denied level; `payment_rejected`/`payment_pending` are track-access errors in HSK 3.0 context. Foreground pending-review status refresh (3s), visibility refresh and action denials reuse the existing rejection/retry/HSK 2.0 dialog; cold starts render a blocked course/practice shell rather than empty screens.
- Course progress, attempts, learner state, mistakes/mastery, XP, and AI budgets are represented by separate model families and services. Preserve server-owned result and access decisions across clients.
- An immutable receipt may claim its preview only once, even after another approved subscription replenishes the user's ticket. Historical duplicate preview budgets deny preview AI without deleting financial/budget facts or overriding independent paid/trial access.
- Course writes lock the canonical user before progress, including map reads that initialize/reset progress. Mini App and the shared Android/Desktop map path use this order so a concurrent track switch cannot lose restored progress. The locked Telegram lookup refreshes already loaded ORM state, preserving consecutive paid renewals and current blocked status. Updated Mini App/Desktop clients send the opened course as a precondition (Mini App `level`, native `expected_level`); a stale course returns `409 course_context_changed` before quota, XP or progress writes. This field never chooses a different course. Legacy omission remains supported; Mini App never relabels another band's saved progress. Private content honors the shared entitlement's admin-configured unlimited Free/Trial decision without consuming a slot; required beginner foundation is checked before lesson reservation and Mini App completion/unlock writes.
- The public website is an informational HSK AI product hub, not a Telegram-only landing page. Public HTML is server-rendered from `app/public_site/content.py` and `app/public_site/render.py`; `app/static/desktop-download.html` is the separate installer page. Shared `/public-assets/navigation.css` and `/public-assets/language.js` provide the common header and locale preference (`tg/ru/uz` for public pages, `tj/ru/uz` for downloader query). Keep original download/referral/release flows intact. SEO implementation/QA: `docs/SEO_DISCOVERABILITY.md`.
- Public-site acquisition stats use `public_site_traffic_daily`: anonymous per-day counts for `utm_source` visits to the homepage or download page, grouped into Instagram, TikTok, YouTube, or other. The admin stats panel shows 7-day, 30-day and all-time counts. Counts are page visits, not unique people; no cookie or account identity is stored. See `app/services/public_site_analytics_service.py`.
- `user_identities` links Google/Apple provider identities to `users.id`. Match accounts by provider subject identity; email/display metadata is not proof of ownership and must not be used to merge accounts.
- Verified account-deletion requests enter `account_deletion_requests` via migration `0101_account_deletion_requests`; each account can have one active request with a 30-day processing target. Purging requires an explicit operator action, and documented financial-retention exceptions remain. Deletion does not cancel external-store renewals; see `docs/ACCOUNT_DELETION_OPERATIONS.md`.

## Native account identity
- Google/Apple first sign-in creates `users.id` only after existing OIDC verification; a known `(provider, subject_hash)` signs into its owner. Telegram private-chat approval can create a new Telegram learner. Email equality and a bound installation never authorize account merging/linking; no fake Telegram ID is stored.
- Android Google provider discovery accepts the confidential browser client pair without the separate native-token audience. Native-token start still requires its own Android client ID before creating a request; browser/native OIDC audiences stay separate.
- Native learning, profile, progress, trial/risk, ad caps, AI budgets, voice and notices use canonical user ownership. Legacy integer service arguments remain real Telegram IDs. Missing Telegram metadata must never become an ownership query matching all NULL rows.
- Native migrations `0103`–`0108` follow `0102_payment_review_preview`, make Telegram metadata nullable and backfill canonical learning/AI/payment/referral owners. `0107` stores optional signup attribution on pending sign-ins. `0108` completes pilot/shadow diagnostics and personal discount ownership: shadow samples dedupe by canonical user/day/action/client/outcome, diagnostic FKs use SET NULL, and personal discounts use `target_user_id` with CASCADE so deleting a target cannot make its offer global. Upgrade refuses conflicting FK contracts or duplicate canonical shadow samples before DDL; downgrade refuses lossy native data. Existing starter access, preview flags/caps, paid dates, trial eligibility, amounts and referral rules remain authoritative.
- Google discovery is flow-specific: shipped Android UI, Mini App linking and macOS/Windows use the browser client ID/secret pair. The optional internal Android Credential Manager path requires its separate Android Web client ID. Browser/native token audiences and nonce namespaces stay separate; an Android-only configuration must not advertise browser Google login.
- Identity changes serialize on the user row and cannot remove the last sign-in method. Approved sign-in proofs retain the exact identity ID; native link proofs retain their originating session ID and are revalidated before use. Blocked accounts cannot refresh; raw session validation remains available for the narrow account-deletion path.
- Native provider attachment start/callback/cancellation revalidate the owning session, device, installation and platform under locks. Cancellation terminates the existing proof without unlinking identities or minting sessions; provider error callbacks burn only their validated pending state. Browser completion uses a fixed, allowlisted wake URI without credentials; only the original native proof poll can finish authentication.
- Desktop sign-in begin, successful token commit and logout advance the native auth generation. Credential writes/deletions and refresh snapshots share the pending-state mutation lock; late start/poll/refresh responses must not restore logged-out credentials or overwrite a newer account, including a refresh begun while replacement sign-in was pending.
- Isolated QA clients use a separate application identity, credential storage and `pomp-hsk-ai-qa` protocol. Android QA disables Firebase/updating and release variants; desktop nonproduction origins require the QA bundle configuration and disable updating. Staging sets `OAUTH_NATIVE_RETURN_SCHEME=pomp-hsk-ai-qa`; default production remains `pomp-hsk-ai`. Never run test signup/migration against production or claim a placeholder-origin compile check is an installable acceptance build.
- Provider-first accounts can explicitly attach an unused real Telegram identity from Android or desktop Profile. A native bearer/session/installation-bound `intent=link` request requires separate private-bot confirmation; it creates no user/session, cannot merge/move an existing Telegram owner, and supports authenticated cancellation. Telegram stays immutable once attached. Existing Google/Apple sign-in proofs remain canonical when Telegram is attached between approval and token exchange.
- Legacy integer ownership queries resolve a real Telegram ID to its canonical user, then include that owner's existing native rows plus unowned legacy Telegram rows. This keeps pre-attachment AI budgets, Voice history and limits shared without rewriting historical transport metadata; conflicting metadata never overrides another canonical owner.
- Direct Android and desktop manual Pro/HSK 3.0 checkout, admin review, paid AI budgets, payment status and Android decision notices use authenticated `users.id`; Google/Apple accounts need no Telegram identity. Both admin surfaces lock the user before reviewing the payment and revoke rejected previews atomically. The one-time HSK 3.0 unlock keeps its own entitlement and never changes Pro terms or restores a preview ticket.
- Admin account management accepts an explicit canonical `user_id`; the strict legacy `telegram_id` adapter never interprets the same number as a canonical account. Conflicting dual targets are rejected. Metrics resolve unowned legacy Telegram aliases to canonical accounts with separate namespaces for orphan histories, preserving metric/cohort definitions. Purge, device inventory and diagnostics give canonical ownership precedence over stale Telegram metadata; approved financial retention is unchanged. Bot-only delivery skips accounts without a positive real Telegram ID while native learners remain in canonical rankings. Affiliate credits derive real Telegram transport from the canonical payment owner, with legacy fallback only for unowned payments.
- Course-track/level mutations lock and refresh the User before progress/track rows, matching HSK 3.0 grants and avoiding grant/switch deadlocks or first-state races. Referral reward-owner updates use the narrower non-key update lock to stay compatible with pending native-message FK key shares; PostgreSQL concurrency regressions cover both lock rules.
- Friend referrals and referral discounts have canonical inviter/invited owners; exact legacy reward, eligibility and device rules remain. Optional signup codes are snapshotted per attempt and applied only when native verified sign-in creates a new account. Existing sign-in/link cannot reattribute. Two successful native Assistant questions qualify using canonical successful-message history, excluding procedural/failed/replayed work without changing quotas. Public trial invites use `/apps?ref=CODE&mode=trial`; legacy Android/iOS discount prefixes retain separate semantics. No automatic Telegram attachment is introduced.
- Play remains consumption-only by the owner's current release decision; store billing is a future phase. Shared HSK 3.0 gates and onboarding omit Play prices/purchase actions. Play silently consumes subscription/trial/discount account offers without promotional Telegram fallback, and keeps neutral course notices. Same-package Direct-to-Play updates clear restored checkout state and cancel persisted Direct update workers/notifications; server entitlements stay authoritative. The website-distributed Direct APK and both desktop platforms use the existing manual checkout. Telegram chat handoff and the separate bot-operated affiliate partner program still require their real Telegram transport. Rollout/test details: `docs/UNIVERSAL_NATIVE_ACCOUNTS.md`.
- Android Assistant answers expose Copy, Share and a per-answer Report action. Both normal and Live Voice answers use the same in-app complaint flow with a snapshot of the selected session/answer and screenshots initially off. Android Assistant guidance permits account/access status help without purchase instructions or external checkout/download steering. Shared normal/Live Voice safety instructions prioritize safety over roleplay/level prompts. Reports use the existing authenticated `/api/v3/android/bug-report` endpoint with `screen=ai_assistant` or `screen=ai_voice`, and an editable answer excerpt. Backend delivery goes to configured Telegram admins and succeeds only after at least one delivery; it is not a durable moderation queue. The tutoring safety prompt does not establish validated output moderation.
- Universal-registration release is on hold: do not merge/push it to `main` or open registration until all seven owner acceptance gates in `docs/UNIVERSAL_NATIVE_ACCOUNTS.md` are evidenced, including Telegram-free Pro purchase, existing-account and cross-client parity, and real-schema staging migration plus backup restore. Unit/integration fixtures alone do not satisfy real provider/staging checks.
- The owner will perform real provider, upstream Voice and installed-client acceptance after code verification. Do not add person-level blocking/fingerprinting for unrelated new Google/Apple identities; the existing canonical account block and linked-provider protections remain.

- Gemini Live supports both provider billing tiers; `GEMINI_BILLING_TIER` records real billing and must not be falsified to enable Live. Explicit Live flag, test Telegram allowlist, authenticated ownership/access checks, time and budget caps still apply to Mini App and native relay. Default rollout remains disabled.

## Important decisions and operational caveats

- Smart Reminder owner-approved D01–D14 product decisions and the sole execution ledger are in `docs/smart-reminders/SMART_REMINDER_MASTER_PLAN.md`. The linked `openspec/changes/smart-reminder-account-orchestrator/` is a validated proposed delta for account-level consent, one study intent per `users.id`/local day, Telegram+Android V1 and later client adapters. It is planning only; runtime, schema, device cutover and production acceptance remain unimplemented. An older offline Android WorkManager sender cannot be proven fenced by server state alone.

- Admin PWA Home/Statistics use first-party `pwa_analytics*.py` section projections, separate from the backward-compatible basic statistics/MCP contract. Each requested section/platform/period reuses an isolated private 24-hour Redis/optional-R2 snapshot under the shared aggregate refresh lease; advanced experiments load only on disclosure. Current auth, payment/access, user/queue and command decisions remain live. Detailed history uses explicit 30-day all-time scope and bounded sentinel reads; missing/immature/over-limit calculations never become fabricated zeros. Financial currency/estimate, cohort, foreground/device and descriptive source-attribution grains are documented in `docs/admin-pwa/READ_PROJECTIONS.md`.
- Admin PWA commands use the owner's single-window interaction: the original editor has a contextual action (Send, Save, Delete, Accept payment, etc.), then directly prepares the exact operation, opens native WebAuthn and executes. Do not restore a separate confirmation screen or generic “confirm with passkey” action. Freeze the input snapshot during preparation/signing, preserve the editor on native cancellation, compare loaded state where available, and retain server-side one-use proof/CAS/audit and uncertain-response no-retry rules.
- Admin PWA launch/resume follows the owner correction merged in PR #209: clear private memory, revoke the previous server session and require a new registered passkey assertion even for a still-valid cookie. Attempt automatic native verification once per foreground visit, retain the browser-gesture fallback and do not restart an active biometric/command sheet. Private dashboard/unread reads start concurrently only after verification. Reopening a queued message job uses the existing fresh signed pending-only resume. This supersedes the earlier cookie-reuse policy; high-risk commands still require their exact operation-bound proof.

- Mini App stroke order uses the public `/api/v3/stroke?char=…` endpoint backed by the versioned Android stroke assets. These assets must remain in server builds. Public requests validate one hanzi and serve bundled data only; unknown characters do not trigger anonymous CDN fetching. Native authenticated stroke lookup keeps its cached fallback.
- Lesson translation tiles grade only the translated meaning; pronunciation/spelling notes belong in pinyin or the grammar explanation. Seed grammar examples feed generated tasks, so keep their translation fields clean. Fix existing task fields in place to preserve section/card material references shared with server mistake validation.
- Localization expansion is **local-first**: author shared translations centrally in GitHub, then generate bundled Android/Mini App/Desktop resources and local Bot/backend catalogs at build/deploy time; never require a per-UI-string runtime API. Keep existing `uz/ru/tj`, native source IDs, entitlements, and client backward compatibility while migrating incrementally. **Continue from `localization/PLAN_SCHEMA_ORDER.md` first** (plan, schema, phase order and verified status), then `docs/I18N_LOCAL_FIRST_WORKPLAN.md` and `localization/surface_registry.json`. P2/P3 runtime integration is authorized on `codex/p3-main-integration-20261020`; main/production promotion remains restricted until the documented CI, access-security and platform QA gates pass.
- Permanent localization rules in `AGENTS.md` and `AI_RULES.md` point to `localization/README.md` for canonical authoring, consumer wiring, UZ/RU/TJ parity, generated-resource checks, locale-code/preference validation, new-language integration and main/release handover; these rules remain after promotion. All UI resource authoring/build ownership is documented there; `scripts/i18n_build_all_catalogs.py` validates every namespace before generating bundled artifacts and safely refreshing content-hash cache tokens in already reviewed HTML. Bot/Desktop/notification/Mini App JSON, native Android XML and structured public-site copy are centrally authored under `localization/`; common/course keys retain their existing owners. Bot handler/formatter/profile templates and backend fixed-copy helpers resolve local catalogs; entitlement formatting changes display text only. Generated delivery files and explicit legacy fallbacks are not independent authoring sources. `localization/review/ui_map_exceptions.json` classifies remaining Python learning/admin/campaign/provider/adapter maps; the adoption guard rejects new or stale entries. Notification DB/campaign overrides keep precedence, and original lesson/graded data stays outside UI bundles. Source generation does not establish authenticated staging or installed-client acceptance.
- Mini App full lesson JSON is served only by signed `GET /api/v3/lesson/content/{level}/{lesson_order}`; it validates Telegram identity, canonical user/level, sequence, required foundation and shared lesson access with `consume=False`/`no-store`. The old `/course_v3_data/{level}/lesson_*.json` route returns 404, and root JSON access is allowlisted to curriculum maps. Keep the bundled UI catalogs and P3 helper scripts in the explicit public asset allowlist. Sales preview, foundation and skip-test have purpose-specific projections: a signed, entitled learner may read at most six skip-test questions for a locked in-range lesson, without consuming quota or unlocking progress; full lesson content/start still enforce sequence. This is implemented on `codex/p3-main-integration-20261020`, not yet on `main`; staging and real-client acceptance remain unverified.
- Keep the HSK course and canonical lesson order/content at the center of the product. Supporting features should not replace the learning path.
- Mini App `朱雀` is a brand league; Android XP tiers remain the server-defined progression. These are separate representations, not interchangeable ranks.
- Play signed preflight validates actual APK/AAB package/version/SDK parity, safe release manifest, forbidden installer/Billing permissions, official bundletool structure and all packaged native ELF/ZIP 16 KB alignment via `android/tools/check_play_artifacts.py`; certificate matching remains a separate signing gate.
- Each Android release must use a `versionCode` greater than the latest published release; it need not increase by exactly one. Verify the artifact against the release manifest because the current workflow does not reject every equal-code/different-artifact case.
- Course/onboarding use a pinned official same-origin Telegram SDK. Preserve the Telegram launch fragment when updating course URLs and navigating between these documents: iOS WebViews may not restore SDK sessionStorage. Never copy launch credentials into query parameters or localStorage; backend signature/expiry validation stays authoritative.
- Source files and repository defaults do not prove live deployment, production environment values, provider credentials, or release status. Verify those in the owning environment before reporting them as live facts.
- New empty QA databases use only the explicitly allowed standalone initializer, never production startup. It preflights the reviewed Alembic head, explicitly registers all ORM models without relying on `app.main` imports (including notification templates), pins the reviewed `EXPECTED_HEAD` in `scripts/qa_standalone_bootstrap.py` and omits its explicit deferred traffic/Admin PWA migration table list from initial ORM creation so their real migrations create them, verifies every ORM table/zero learner rows, and refuses nonempty targets. A new Railway QA project must be explicitly bound to its actual project ID, database and origin; existing QA allowlists must not be bypassed. Never rerun the empty initializer to repair a QA database containing learner activity.
- Railway SSH can omit the running container process's `LD_LIBRARY_PATH`. A native-module import failure from an SSH shell alone is not evidence of a broken application image: repeat the read-only probe with the actual application process's library path before changing build packages.
