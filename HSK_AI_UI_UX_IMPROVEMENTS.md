## UIUX-001 — Unified Header System

**Статус:** ✅ УТВЕРЖДЕНО владельцем — 2026-11-12. Зафиксировано для итогового задания Codex; реализацию пока не начинать.

### Проблема
По 15 скриншотам (IMG_6793–IMG_6807) верхние заголовки и навигационные элементы выглядят несогласованно: отличается вертикальная привязка, кегль и насыщенность, горизонтальное положение, исполнение кнопки «назад», расстояние до содержимого. Разница особенно заметна между основными вкладками («HSK 1», «Практика», «AI Voice», «Рейтинг», «Профиль») и вложенными страницами («Словарь иероглифов», «Мои ошибки», «Настройки», «Уведомления», «Друзья»).

### Предлагаемое решение
Внедрить **один переиспользуемый набор Header/AppBar-компонентов** и токены размеров/отступов вместо локального произвольного позиционирования.

**А. Основные вкладки — RootHeader**
- Строка заголовка высотой **56 pt на iOS/PWA**, **56 dp на Android**, начиная сразу после системного safe area / status bar.
- Заголовок слева, одинаковая базовая линия и единая типографика: ориентир **22/28, semibold** (при необходимости согласовать с существующим шрифтом бренда).
- Горизонтальный отступ **16**; служебные индикаторы, счётчики и иконки справа — в той же строке, вертикально центрированы.
- Подзаголовки («Закрепление и проверка» и т. п.) — отдельно под основной строкой: заголовок при этом не смещается между вкладками.

**Б. Вложенные страницы — DetailHeader**
- Та же строка **56 pt/dp**, выравнивание после safe area; слева кнопка назад с нажимаемой областью минимум **44×44 pt (PWA/iOS)** / **48×48 dp (Android)**.
- Затем заголовок на одной устойчивой базовой линии: ориентир **20/26, semibold**. Один выбранный шаблон выравнивания для однотипных экранов (рекомендация — заголовок рядом со стрелкой, слева; не чередовать произвольно с центрированием).
- Кнопки действий и счётчики справа; одинаковые отступы и размеры иконок.
- Разделитель под строкой только там, где он функционально нужен, а не на отдельных страницах по случайному принципу.
- Для страниц с поиском (IMG_6799) допускается **SearchHeader** как подвид: назад + поле поиска в той же стандартной строке; не добавлять дублирующий заголовок без UX-причины.

**В. Полноэкранные режимы — ImmersiveHeader**
- Уроки/тесты (IMG_6800, IMG_6801): стандартная safe-area и область управления, но вместо текстового заголовка — кнопка назад + индикатор прогресса + счётчик.
- AI Voice-сессия (IMG_6803): оставить полноэкранную композицию; упорядочить только отступы и зоны нажатия элементов управления. Не навязывать обычный заголовок.
- Экран профиля другого пользователя (IMG_6804): крупное имя в содержимом сохранить; верхняя навигационная строка должна иметь согласованную высоту. Компактное имя в верхней строке — только если требуется дизайном/прокруткой, без дублирования на экране.

### Общие правила
- Высоту строк считать **от нижней границы safe area**, не задавать абсолютную координату экрана; учитывать iPhone Dynamic Island / Safari vs установленная PWA / Android status bar.
- Сетка отступов 4/8/12/16/24; первый блок контента стартует после одинакового **12–16**-единичного промежутка для однотипных экранов, исключая специальные hero/overlays.
- Никаких layout shift при skeleton/loading: заголовок и системные контролы остаются видимыми, скелетон заменяет только загружаемый контент (особенно рейтинг IMG_6796).
- Переводы TJ/RU/UZ и длинные заголовки: безопасное ограничение текста или адаптация, без наложения на иконки; Dynamic Type / font scaling, светлая/тёмная тема по реально поддерживаемым режимам.
- Верхние действия: стабильные hit-area и единые состояния hover/press/focus, корректная работа с VoiceOver/TalkBack.
- Не вмешиваться в контент/бизнес-логику, анимации, маршрутизацию и функции экрана без отдельного согласованного задания.

### Карта затронутых скриншотов
- RootHeader: IMG_6793, 6794, 6795, 6796, 6797.
- DetailHeader: IMG_6798, 6802, 6805, 6806; IMG_6807 — проверить характер перехода из профиля и нужность кнопки назад.
- SearchHeader: IMG_6799.
- ImmersiveHeader: IMG_6800, 6801, 6803; контекстный профиль IMG_6804.

### Критерии приёмки для будущей реализации
1. Во всех пяти основных вкладках верх заголовка находится на одной вертикальной сетке и не прыгает при переходах.
2. Вложенные экраны используют единый вид и выравнивание back/title/actions, за исключением документированных типов SearchHeader и ImmersiveHeader.
3. Ни один header не перекрывается status bar, Dynamic Island, клавиатурой, content или bottom navigation.
4. Проверить PWA Safari и Home Screen, Android на малом и большом экране, RU/TJ/UZ и длинные заголовки.
5. Прогон регрессии навигации, accessibility и skeleton; без изменений бизнес-логики.

**Решение владельца (2026-11-12):** UIUX-001 Unified Header System утверждён целиком. Включить в итоговое задание для Codex вместе с остальными согласованными пунктами. Пока не отправлять Codex.

## UIUX-002 — Personal Progress Hub: XP, Streak, цели и достижения

**Статус:** ✅ УТВЕРЖДЕНО владельцем — 2026-11-12. Зафиксировано для итогового задания Codex; **не реализовывать до завершения общего обсуждения**.
**Источник:** скриншоты верхних индикаторов курса, выбора цели на 7/14/30/50 дней и достижений профиля (2026-11-12).
**Платформы:** PWA (iPhone) + Android native, с общей серверной моделью данных.

### Проверенные факты кода (read-only аудит GitHub)

Репозиторий `akbarholturaev11-lang/HSK-AI-Bot`, ветка `main`, HEAD при проверке: `680761f15e05f6d543da52cd021d05df41217ea3`. Перед реализацией **снова** проверить актуальный `main`.

- `app/static/course-v3.html` (~строки 4113–4114): 🔥 — `MAP.progress.streak`, 💎 — `MAP.progress.xp`. Алмазы **не являются внутренней валютой**. Никаких «балансов кристаллов», их расходования или магазина не добавлять.
- `app/services/course_gamification_service.py`: `xp_total`, `daily_xp`, `weekly_xp`, `streak`, `longest_streak`, `week_activity_dates`; начисление через `CourseXpEvent`, защита от дубликатов по `activity_ref`, +5 XP за первую активность дня. Сохранить серверную проверку.
- `app/services/onboarding_goal_selection.py` и `app/db/models/course_miniapp_profile.py`: допустимые `streak_target_days` = 7/14/30/50, хранение выбранной цели уже есть. Цель — намерение пользователя, не замена реального streak.
- `app/static/course_v3_li_onboarding.html` (~строки 681–687): экран выбора этих целей уже реализован в onboarding. Отображение «7» на иллюстрации при отсутствии выбора — UI fallback, а не подтверждённая выбранная цель.
- `app/static/course-v3.html` (~строки 7670–7702): профиль уже показывает прогресс достижений «100 уроков» и «30 дней подряд». Это показатели достижений, а не обязательно пользовательская персональная цель.
- `app/services/course_miniapp_profile_service.py`: пользовательский `daily_goal_xp` уже хранится отдельно от streak target; нельзя путать дневную норму XP и цель по дням.
- Примеры фактических XP-баз: `app/services/course_miniapp_lesson_flow_service.py` — секция +8, глава +12, урок книги +20; `app/services/course_miniapp_practice_service.py` — тренировка +8, тест +10. Возможный бонус первого действия дня +5; точные значения должны выводиться из текущей серверной логики, а не дублироваться в текстовых константах клиента. Проверить остальные виды активностей перед реализацией полного справочника.

### Проблема

В верхней строке курса указаны два числа без пояснения их природы, прогресса и действия по нажатию. Отдельные экраны streak target и достижений уже есть, но пользователь не видит их как единую систему. Предыдущая гипотеза про «кристаллы» была неверной.

### Утверждённое UX-решение — две полноэкранные страницы

**1. Верхний индикатор 🔥 → отдельная полноэкранная страница Streak.**
- Верхний hero-блок с крупным реальным числом дней в серии, выбранной личной целью (`2 / 7 дней` только если **реально выбрано 7**), лаконичным progress bar и подписью «осталось N дней». Без гигантского контейнера вокруг всей страницы.
- Отдельная аккуратная карточка календаря **месяца** с навигацией по месяцам (по образцу полезной идеи Duolingo, но в фирменном светлом стиле HSK AI). Различать подтверждённые активные дни, прошедшие без активности, сегодняшний день и будущие даты. Показывать историю только за реально доступный серверный период; если API отдаёт лишь неделю — прежде проверить и при необходимости минимально расширить read-only источник, без синтетических заполнений.
- Отдельная компактная карточка личной цели / следующего рубежа; не выдавать 30-дневное достижение за выбранную 7-дневную цель.
- Кнопка «Изменить цель» открывает/переиспользует уже существующий выбор 7/14/30/50 дней; после сохранения новый target отражается в профиле и курсе. Не создавать вторую независимую модель. Смена цели не сбрасывает накопленный streak.
- Короткое, точное объяснение, какое подтверждённое учебное действие сохраняет streak; кнопка «Продолжить обучение» — на уже существующий релевантный маршрут.
- Если цель не выбрана (legacy), предложить выбрать без ложной установки по умолчанию. Не смешивать `longest_streak`/текущий streak/выбранную цель.

**2. Верхний индикатор 💎 → отдельная полноэкранная страница XP.**
- Вверху крупное общее XP с ясной подписью «Всего XP» (это опыт, **не валюта**). Ниже — отдельные компактные карточки «Сегодня» (фактический прогресс к дневной XP-цели) и «На этой неделе» из актуального backend snapshot, без повторения гигантских чисел в каждой карточке; никакой выдуманной валюты или расходов.
- Блок «За что начисляется XP»: только реально поддерживаемые активности и подтверждённые правила начисления; допускаются различия по режиму / уровень в соответствии с сервером.
- Краткая история начислений только из проверенных событий `CourseXpEvent` после аудита доступности/безопасности API; если endpoint нет, добавить минимальный read-only API с ограниченной выдачей, без нового учёта баллов и без подмены аналитикой.
- Не показывать неподтверждённые награды, виртуальный магазин или функции «скоро» только ради заполнения экрана.

**3. Профиль → существующий блок достижений.**
- **Уточнено более поздним UIUX-005:** в профиле оставить компактное достижение «100 уроков», а отдельную дублирующую карточку «30 дней подряд» убрать; текущий streak отображается в существующем компактном календаре и подробно раскрывается на странице UIUX-002. В разделе Streak сохранить различие личной цели и 30-дневного достижения.
- Streak target (например 7 дней) и достижение «30 дней подряд» — две разные сущности. Показывать их понятно и не заменять одно другим. При необходимости отдельная лаконичная ссылка на личную цель, без дублирования полноценной панели на профиле.
- Переиспользовать существующие массивы активных дат, счётчики уроков и API; не плодить дублирующие запросы и разные источники истины.

### Правила дизайна и технической реализации

- Сохранить фирменные оранжевый 🔥 и золотой 💎, визуальную связь с пандой и оформление курса; не перегружать карточки конфетти и агрессивными анимациями.
- Сохранять единый header, отступы и типографику из UIUX-001; hit-area >= 44×44 pt на iOS/PWA и >= 48×48 dp на Android.
- **Оба индикатора открывают самостоятельные ПОЛНОЭКРАННЫЕ страницы**, а НЕ bottom sheet. У каждой страницы — единый DetailHeader/кнопка «Назад» по UIUX-001, штатное возвращение в точку открытия, безопасная работа с safe areas и системной навигацией. Не создавать overlay поверх overlay.
- **Композиция:** свободный вертикально прокручиваемый экран с 2–4 смысловыми группами; внутри отдельные минималистичные карточки с умеренными скруглениями, без тяжёлых рамок, слоёв «карточка в карточке», ненужных теней и декоративного шума. Не заворачивать весь экран в одну большую карточку.
- **Streak:** крупный hero числа дней + месячный календарь + отдельная карточка личной цели; **XP:** крупный общий счётчик + дневной прогресс + понятные способы заработать XP + история начислений (при подтверждённом API).
- Сохранить HSK AI light/cream визуальный язык, фирменную панду там, где она уместна, и спокойные микроанимации; вдохновляться информационной архитектурой Duolingo, не копировать его тёмную тему или визуальные элементы 1:1.
- Если изменение цели требует отдельного экрана, переиспользовать существующий выбор 7/14/30/50 дней с корректным возвратом; без лишних цепочек модальных окон.
- RU/UZ/TJ, локальные даты и часовые пояса; правильно показывать 0 XP, 0 streak, давно неактивную серию, незаданную цель, loading/empty/error/retry; не отображать выдуманные события.
- Не ломать XP-award, антидублирование, подсчёт streak, learning flow, оптимизацию под PWA/Android. Изменения gameplay/наград отдельного согласования требуют.

### Критерии приёмки

1. 🔥 число равно серверному текущему streak; модуль показывает сохранённую цель и её изменение без сброса streak.
2. 💎 число равно суммарному XP, никогда не именуется «кристаллами» и не показывает расходование.
3. Дневной XP прогресс курса и XP-окна совпадает по одной дате/таймзоне; профайл-ачивки считаются из реальных данных.
4. Список «где заработать XP» отражает фактические award paths; сервер остаётся единственным источником начисления.
5. Не появляется новое начисление при повторном открытии окон, не создаются дубли и лишние запросы; корректные loading/error/empty состояния.
6. PWA Safari/installed PWA и Android работают с одинаковой семантикой и нативными жестами; RU/TJ/UZ и доступность проверены.

**Решение владельца (2026-11-12):** концепция UIUX-002 утверждена: **два отдельных полноэкранных экрана** 🔥 Streak и 💎 XP, **не bottom sheets**, с минималистичными карточками внутри, сохраняющими визуальный стиль HSK AI. Месячный календарь streak, личная цель и XP-история должны показывать только реальные доступные данные; перед реализацией Codex обязан перепроверить текущий `main` и существующие API. Реализацию не начинать до завершения обсуждения остальных пунктов.

## UIUX-003 — Smart Dictionary Filter + ⭐ «Сохранённые»

**Статус:** ✅ УТВЕРЖДЕНО владельцем — 2026-11-12. Дополнение ⭐ «Сохранённые» утверждено как часть того же пункта. Реализацию не начинать до завершения UI/UX обсуждения.
**Платформы:** learner PWA / iPhone и native Android (Play/direct). **Источник:** скриншоты словаря и раздела «Готовые фразы» (IMG_6814, IMG_6815).

### Проблема и цель

Сейчас словарь показывает две горизонтальные строки выбора версии («Все версии», «HSK 2.0», «HSK 3.0») и уровня («Все уровни», «HSK 1» и т.д.), что перегружает интерфейс. В обычном сценарии пользователь уже выбрал версию курса, поэтому нет необходимости повторно выбирать её внутри словаря. Нужен лёгкий способ помечать слова ☆/★ и открывать только сохранённые, по образцу существующего списка готовых фраз.

### Факты read-only аудита кода GitHub

Репозиторий `akbarholturaev11-lang/HSK-AI-Bot`, `main`, HEAD при аудите `680761f15e05f6d543da52cd021d05df41217ea3`. Перед реализацией Codex снова сверяет актуальный `main`.

- `app/static/hsk-lugat.html`: `currentVersionFilter` при отсутствии явного параметра по умолчанию `all`; `currentFilterLevel`, `levelsForVersion()`, `renderFilterRows()` формируют две строки. Слова из HSK 2.0 / 3.0 объединяются и фильтруются по тегам `lv`. Функции `rebuildActiveWords()` и `wordMatchesFilter()` управляют списком. В этом файле функциональность избранных слов не найдена.
- `app/static/course-v3.html`, блок `RESOURCE.url('dict')`: в адрес словаря передаётся текущий `level` / `filter`, но не явный идентификатор выбранной версии курса. При дальнейшей реализации передать и версию, либо безопасно получить её из актуального общего состояния.

- `app/services/course_v3_dictionary.py`: словарь для клиентов собирается из двух источников HSK 2.0 и HSK 3.0; повторяющиеся иероглифические формы могут быть объединены с несколькими тегами уровня. Не удалять и не дублировать существующие словарные данные, корректно показывать членство выбранной версии.

### Утверждённое поведение

1. **Версия курса выбирается автоматически:** если курс HSK 2.0 — словарь показывает только слова HSK 2.0, если HSK 3.0 — только слова HSK 3.0. На обычном экране словаря удалить строку «Все версии / HSK 2.0 / HSK 3.0» и лишнюю кнопку сложных фильтров, если та больше не нужна. Версия обозначается компактным непереключаемым индикатором `HSK 2.0` / `HSK 3.0`; управляется уже существующей настройкой курса. При открытии словаря вне курса — использовать актуальную выбранную версию из авторизованного состояния, не угадывать её из языкового уровня или кеша другого аккаунта.
2. **Одна строка фильтров уровня:** `Все`, `HSK 1`, `HSK 2` и т.д. — только реально поддерживаемые уровни выбранной версии. По умолчанию `Все`, то есть **все доступные слова выбранной версии**, без лишних слов другой версии. Поиск работает в выбранной версии и текущем уровне.
3. **⭐ «Сохранённые» как компактный фильтр-пилюля** в этой же строке. Нажатие включает просмотр только отмеченных слов (в пределах текущей версии и, если выбран, уровня); повторное нажатие возвращает полный набор. Визуально активное состояние ясно выделено. Пустой результат — спокойное локализованное пояснение и путь к обычному списку.
4. **☆/★ у каждого слова:** нажатие на ☆ помечает слово, становится ★; повторное нажатие удаляет из сохранённых. Слова не удаляются из словаря. Реакция немедленная (с обработкой ошибки сохранения и откатом при отказе), доступная зона касания и озвучиваемые `aria-label` / TalkBack; не конфликтует с открытием карточки слова. Звёздочка в карточке детали, если она там появится, отражает тот же статус.
5. **Сохранённые слова привязаны к аккаунту и синхронизируются между PWA и Android:** при реализации сначала проверить доступные сервисы/хранилища и переиспользовать существующие ID / auth / API-контракты; если их нет — добавить минимальный защищённый серверный контракт read / toggle для словаря. Не копировать локальный механизм готовых фраз как окончательный вариант. Если пользователь ещё не авторизован — отдельно определить безопасный локальный режим и последующее объединение, не смешивая записи разных аккаунтов.
6. **Смена версии не удаляет избранные:** сохранённые слова, относящиеся к другой версии, остаются в профиле, но обычный фильтр текущей версии их не показывает. Стабильная идентичность слова и теги версии нужны для корректного поведения на пересечении двух словарей; избегать неуникальных индексных ID и дублей одного слова.
7. **Согласованность интерфейса:** визуальные стили плашек, ☆/★ и термин «Сохранённые» согласовать с существующим экраном готовых фраз. Заголовок и back соответствуют UIUX-001. Не затрагивать поиск по hanzi / pinyin / переводу, порядок черт, упражнения, кэш, избранное готовых фраз и прогресс уроков.

### Условия приёмки

- Пользователь HSK 2.0/3.0 видит с первого открытия только слова выбранной версии; уровень по умолчанию «Все», строка версии не дублируется.
- Фильтры уровня, поисковая строка и ⭐ «Сохранённые» применяются предсказуемо; сброс поисковой строки не стирает пометки.
- ☆/★ можно менять в списке без открытия детали и без случайной навигации; пустой список сохранённых обработан.
- Пометки сохраняются после повторного входа и отображаются тем же аккаунтом на PWA и Android; смена HSK версии и последующее возвращение ничего не удаляют.
- Одинаковое поведение на Android (Play/direct), Safari и установленной PWA, с локализацией RU / UZ / TJ, доступностью, skeleton/empty/error/retry.
- Существующие сохранённые **фразы** не затрагиваются; миграция или совместное хранилище только при обоснованной необходимости.

**Решение владельца (2026-11-12):** UIUX-003 Smart Dictionary Filter одобрен. Дополнение к пункту: как в «Готовых фразах», добавить ☆/★ сохранение отдельных слов и фильтр ⭐ «Сохранённые». Никакой реализации до завершения обсуждения и передачи итогового плана Codex.

## UIUX-004 — Готовые фразы: компактные раскрывающиеся карточки и аудио

**Статус:** ✅ **УТВЕРЖДЕНО владельцем — 2026-11-12**. Финальный вариант: по умолчанию карточка свёрнута; видны только китайская фраза, ☆/★, 🔊 и ненавязчивый chevron; пиньинь, перевод, категория и копирование появляются только при раскрытии. Реализацию не начинать до завершения общего UI/UX обсуждения и отдельной передачи Codex.

**Платформы:** learner PWA и native Android. **Источник:** скриншоты раздела «Практика → Готовые фразы» (IMG_6816 и D13F9E27).

### Проблема

Все фразы сейчас показаны полностью раскрытыми: много вертикального пространства занимают категория и текстовая кнопка «Копировать», поэтому за один экран видно мало фраз. Цель — ускорить просмотр и сохранить быстрые полезные действия.

### Утверждённый компактный вид

- **Свёрнутая карточка (collapsed) показывает ТОЛЬКО китайскую фразу (иероглифы), компактные, сразу доступные ☆/★ «Сохранить / Сохранено» и 🔊 «Прослушать», а также ненавязчивый chevron раскрытия. Пиньинь, перевод, категория и копирование в свёрнутом состоянии НЕ показываются.** Кнопки ☆/★ и 🔊 не требуют предварительного раскрытия карточки.
- Нажатия на ☆/★ и 🔊 не должны вызывать раскрытие/закрытие карточки. У каждой кнопки отдельная область касания, понятное активное/воспроизводящее состояние и доступная локализованная метка.

### Утверждённое поведение раскрытия и действий

1. Нажатие на свободную область строки/карточки раскрывает её; мягкий короткий переход, без прыжков и затруднения прокрутки. Небольшой chevron показывает возможность раскрытия.
2. При раскрытии показываются **пиньинь и перевод**, затем категория и действие копирования; большую кнопку «Копировать» заменить **иконкой** с подтверждением «Скопировано». В свёрнутом состоянии видны только иероглифы, ☆/★, 🔊 и chevron; **ни пиньиня, ни перевода, ни категории, ни копирования**. Сохранение и аудио доступны без раскрытия.
3. По умолчанию все карточки свёрнуты; **одновременно раскрыта не более одной карточки**. При раскрытии другой предыдущая сворачивается. Не нарушать поиск, категории и фильтр «Сохранённые».
4. Аудио произносит только китайский текст текущей фразы, без автозапуска при скролле или раскрытии. По нажатию на 🔊 доступны loading, playing, stop/error; перед реализацией проверить существующий TTS/кэш и права в PWA/Android, не дублировать сервисы.
5. Сохранение ☆/★ должно продолжать использовать существующую функциональность готовых фраз. Не путать её со **сохранёнными словами словаря** из UIUX-003.
6. Поддержать RU/UZ/TJ, фокус и screen reader, PWA Safari / installed PWA / Android и плавную работу длинного списка.

**Финальное решение владельца (2026-11-12):** UIUX-004 утверждён целиком в уточнённом виде. Свернутая карточка = **только иероглифы + ☆/★ + 🔊 + chevron**. По нажатию на саму карточку = **пиньинь, перевод, категория и компактное копирование**. Одновременно не более одной открытой карточки. Звёздочка и аудио работают независимо от раскрытия. Никаких изменений в коде продукта и передачи Codex до отдельного финального распоряжения.

### 1. Обязательный сценарий внутри урока (главное требование)

1. Ученик проходит заранее подготовленную часть HSK 2.0/3.0. Сервер получает достоверные результаты имеющихся проверяемых заданий и определяет `user_id`, учебный `target` (слово/иероглиф/грамматическая конструкция), **конкретный навык** (значение, hanzi, pinyin/тон, listening, порядок слов, грамматика), исходный урок, формат, время и идентификатор попытки. Не выводить ошибку исключительно из UI-клика, самостоятельно поставленного ✅/❌ или сырого ответа LLM/ASR.
2. Повторяемая либо достаточно достоверная ошибка повышает приоритет **именно соответствующего навыка**. Одно случайное неверное нажатие не должно объявлять весь китайский иероглиф «невыученным». Например, `收到` (shōudào — получить) можно понимать по смыслу, но путать тон или pinyin; назначать упражнение на pinyin/слух, а не бессистемно проверять значение.
3. При открытии **следующего обычного урока** сервер отдельно готовит `Adaptive Lesson Plan`: неизменяемый на время попытки персональный набор проверок по изученным ранее слабым targets, срокам повторения, доступным форматам, HSK track/level, языку и возможностям клиента. Использовать `CourseMistakeTargetStore` и подходящие элементы существующего SRS/review; не создавать LLM-генерацию полного урока и не подмешивать ещё не изученные слова.
4. Клиент собирает видимый поток: **обычные карточки урока + редкие адаптивные карточки в естественных точках между ними**, без отдельной вкладки, блока «Ошибки» или обязательной промежуточной мини-сессии. Пример для объяснения, **не нормативная пропорция**: 10 обычных проверяемых упражнений и 2 дополнительные персональные проверки, распределённые по уроку. Начальные лимиты, места вставок, переносимость между частями и исключения для checkpoint/exit-ticket определить аудитом UX и тестами; не вытеснять новые задания и не добавлять бесконечный цикл.
5. После ответа отдельный серверный обработчик проверяет адаптивное задание **по сохранённому каноническому snapshot/ключу**, а не по переданному клиентом `correct_index` или произвольному `target_id`. Точный формат результата обновляет только персональное освоение/расписание следующего повторения, без XP и без записи «завершён урок». Достоверные самостоятельные верные ответы **в разные моменты и/или форматах** постепенно снижают частоту повторения; новая проверенная ошибка возвращает target в очередь.
6. Адаптивный модуль **не является gate**. Неверный ответ, отсутствие ответа, отключение feature flag, таймаут, отсутствие подходящего задания или неподдерживаемый формат **не блокируют основной урок, оценку, переход к следующей части или доступ**. В таком случае исходный урок исполняется без адаптивной надстройки.

### 2. Архитектура без изменения канонического урока

**Принцип: НЕ править и НЕ переупорядочивать** хранимые `app/static/course_v3_data/<level>/lesson_XX.json`, исходные `sections[].cards`, `exit_ticket`, их card indices и существующие `material_ref`. Не вставлять персональные задания в канонический JSON с изменением позиций: это может исказить привязку «Мои ошибки», Android-парсер, PWA-кэш и возобновление сессии.

```text
Заранее подготовленный Course v3 JSON ───────────────────────────┐
                                                                 ├─► Client lesson presentation
POST/GET adaptive plan (подтверждённый account, track, lesson) ──┘    обычная карточка → адаптивная → обычная ...
           ▲                                  │
  Mistake Targets + Word Mastery + signals    └─► отдельная server-verified adaptive answer
           ▲                                                    │
   Достоверные попытки                                          ▼
                                                 learner skill state / SRS due

Отдельно, БЕЗ ИЗМЕНЕНИЙ: canonical grading → Course Progress / unlock / XP / official analytics
```

- **Общий backend-движок выбора, два тонких presentation adapter'а:** iPhone PWA (`course-v3.html`/обычная очередь карт) и Android (`LessonParser.kt`/`LessonViewModel.kt`); каждое приложение отображает **те же target/skill/проверенные задания** в собственных поддерживаемых карточных форматах. Не считать существующие Mini App section-flow и native Course v3 идентичными по подсчёту результатов. Не развивать Desktop-only функции в рамках этой задачи.
- **Sidecar plan** в отдельном authenticated API/поле с явной версией контракта, `attempt_id`/`session_id`, `question_id`, `target_key`, `skill`, форматом, допустимым временным окном, безопасным placement-правилом и идентификатором snapshot. Его идентификаторы **не должны** совпадать с `lesson:<level>:...:card:<n>` или подделывать исходный `material_ref`. Состояние набора фиксируется сервером на попытку; повторные GET/retry возвращают тот же набор до его законного обновления. Точный транспорт выбирается после проверки PWA/Android контрактов.
- **Раздельная оценка и запись:** основной lesson grading/completion продолжает использовать неизменённую базовую очередь и текущие server-authoritative права/правила. Дополнительная карточка не учитывается ни в знаменателе/числителе основной оценки, ни в `course_progress`, `CourseAttempt`, XP, наградах, rank, streak, сердечках или проценте прохождения урока. В ответах/аналитике отдельное происхождение `adaptive_review`, не `lesson_completed` и не `section_attempt_scored`.
- **Серверный приём результата:** проверить личность, принадлежность lesson/HSK track, доступность snapshot, `question_id`, принадлежность target, формат, единственность и факт отправки ответа; записать идемпотентно, в транзакции, без повторных начислений и двойного усиления одного evidence. На Android текущий `complete()` главным образом принимает завершение и канонизированные *ошибки*, а не серверно оценённые ответы по всем карточкам; для адаптивных ответов требуется **отдельный подтверждённый протокол**, нельзя просто дописать их в `mistakes` при завершении.
- **Возобновление/кэш:** PWA `LESSON_DATA_CACHE`, `saveLessonResume`/`restoreLessonMastery`, Android disk/offline lesson cache и индекс карточки зависят от стабильной базовой очереди. При восстановлении adaptive вставок сохранять/восстанавливать базовый cursor отдельно от персональных вставок, не менять `material_ref` и не терять ответы при смене сети. При смене аккаунта/уровня/HSK 2.0↔3.0 не переносить чужой или несовместимый sidecar plan. Предусмотреть дедуп offline sync и обновление планов только между безопасными границами попыток.
- **Форматы и качество:** переиспользовать `mistake_drill_factory.validate_question` и существующие локализации UZ/RU/TJ, TTS/аудио и capability checks. Для listening обязательна реальная аудиоподдержка, для grammar — корректное предложение; не превращать неподдерживаемый формат в бессмысленный MCQ и не раскрывать ответ до проверки. Избегать повторов того же вопроса/порядка ответов, держать новые материалы и тестовые checkpoints неприкосновенными.

### 3. Отделение от «Мои ошибки», карточек и AI Voice

- **Основной продуктовый эффект — именно в обычном курсе.** Не добавлять обязательную кнопку «Пометить для повторения»; отдельная страница «Мои ошибки» остаётся **дополнительным ручным входом**, работает по своим существующим контрактам и использует совместимые targets/state. Адаптивные упражнения не требуют посещения этой страницы.
- `UIUX-008 / COURSE-FLASHCARDS-001` — возможный **формат** отдельных встроенных карточек; flip/«Знаю»/«Повторить» = **self-assessment**, это не проверенная ошибка и не подтверждённое освоение. Для обновления мастерства нужна настоящая проверяемая форма ответа. Не считать каждое ✅ отдельным правильным ответом.
- Practice / Daily Plan / Smart Reminder / AI Voice могут в будущих согласованных интеграциях **читать общий подтверждённый learning state**, но не становятся обязательным отдельным UI или параллельной реализацией в рамках этого уточнения. Особенно **не переопределять** текущие voice modes, лимиты, стоимость, exam/placement scoring и работу действующей страницы «Мои ошибки» без отдельного согласования.

### 4. Интеграционные зависимости и rollout

- **Analytics Integrity** (к моменту внедрения): отличать `adaptive_assigned`, `adaptive_shown`, `adaptive_answer_verified`, `adaptive_due`, `adaptive_relearned` от основного lesson score/completion; использовать существующий event registry/dedupe/attribution, не создавать вторую телеметрию. Измерять independent recall спустя интервал, частоту повторов, вовлечённость, отклонения в completion и отказы. События сами по себе **не** источник master-state.
- **Monitoring:** только технические сбои сборки плана, рассинхрон версий, stale snapshot, ответ вне нужного пользователя, невозможность проверить задание; обычная ошибка ученика **не инцидент**. Мониторинг не должен тормозить урок.
- **Performance/Smart Render:** bounded queries и кэш только по безопасным ключам пользователя/уровня/ревизии; не делать N+1 по каждому target, не задерживать first render из-за optional personalization. При сбое/timeout — обычный урок и незаметная деградация без потери прогресса.
- **Порядок работ:** (1) свежий audit двух delivery paths, оценки и identity/refs; (2) schema/contract и snapshot без UI; (3) подбор/верификация с shadow mode и unit tests; (4) PWA/Android interleave и корректное возобновление; (5) end-to-end + реальные Safari/Home Screen и Android Play/direct; (6) feature flag, ограниченный rollout, метрики, мгновенный rollback только adaptive overlay.

### 5. Приёмочные критерии (обязательные)

1. В HSK 2.0/3.0, UZ/RU/TJ и в PWA/Android на одном и том же **обычном** lesson flow появляются уместные персональные задания по ранее подтверждённой слабости, **между обычными карточками**, без отдельного блока «Мои ошибки» и без изменения оригинального lesson JSON.
2. Базовая оценка, XP, награды, hearts/streak, unlock, course progress, completion и лимиты **до и после включения адаптации идентичны при одинаковых основных ответах**; дополнительная ошибка не снижает балл и не мешает завершению; дополнительный успех не даёт лишний XP.
3. Один слабый навык не превращается в «не знает всё слово»; успешная самостоятельная проверка обновляет только соответствующий target/skill, а следующая due-проверка выбирается согласно доказанному расписанию. Отдельная самооценка flip-карточки не засчитывается как проверенный ответ.
4. Подмена `question_id`, forged answer, повторная отправка, смена аккаунта, track, языка, офлайн-восстановление, старый кеш, stale snapshot, отсутствующий renderer или таймаут не нарушают безопасность, историю ошибок и прогресс. Варианты N1 checkpoint / exit-ticket и старые lesson material refs остаются корректными.
5. Контрактные, unit, integration, e2e и real-device проверки подтверждают отсутствие регрессий обычных уроков, PWA/Android, XP/счётчиков, Analytics/Monitoring, загрузки и учебных источников. Flag OFF гарантированно возвращает исходную неадаптивную очередь без миграции назад.

### 6. Передача в реальный план модуля «Курс»

**При финальной передаче Codex обязательна именно эта пересмотренная версия `COURSE-ADAPTIVE-001`.** Внести её в **один актуальный** Course Plan/OpenSpec, указав интеграционные тесты PWA/Android и явную границу между обычным курсом и дополнительной адаптивной проверкой. **Не восстанавливать прежнюю концепцию**, где главным UX становилась страница «Мои ошибки» или параллельный AI Voice flow, и не создавать вторую независимую систему курса. Текущие записи в этой Library — только подготовка будущего задания; GitHub и производственный код сейчас не изменяются.

**Окончательное решение владельца (2026-11-13):** адаптивные задания **визуально находятся внутри обычных уроков**, но логически/серверно отдельно проверяются, влияют **только на персональное обучение и повторение**, **не влияют на обычный урок, XP и progress**, не блокируют продолжение. Это **замена** ранее описанному сценарию UIUX-007, а не новая задача вдобавок к нему.

## UIUX-008 / COURSE-FLASHCARDS-001 — Интерактивные карточки внутри уроков и персональных повторений

**Статус:** ✅ ЗАФИКСИРОВАНО ПО ПРЯМОМУ ТРЕБОВАНИЮ ВЛАДЕЛЬЦА (2026-11-12); конкретные форматы, объём вставок и интеграционные контракты определить после повторного аудита актуального `main`. Это **дополнение к курсу и к UIUX-007 / COURSE-ADAPTIVE-001**, а не отдельное новое приложение. Реализацию пока **не начинать**.

**Референс:** предоставлены `IMG_6837.png` и `ScreenRecording_11-12-2026 20-10-40_1.mp4` (14-секундная запись). В референсе показаны: карточка с крупным китайским словом, открытие ответа с пиньинем/значением/примером, действия ❌/✅ для самооценки, кнопка 🔊, прогресс вида `8 из 25`, завершение с итогом и действиями повторить/продолжить. **Заимствовать паттерн обучения, не копировать UI ChatGPT, цвета, чужую айдентику, текст или декоративные оболочки.** Использовать дизайн-систему HSK AI, согласованный UIUX-001 и визуальные стандарты уроков.

### 1. Обязательная учебная механика

1. В обычных уроках **встроить компактные карточные задания** на слова, иероглифы, pinyin, значение, контекст и, где поддерживается, распознавание на слух. Это один из типов заданий в существующем lesson renderer, **не замена** диалога, грамматики, теста, аудио, homework или других работающих форматов. Показывать по смыслу изучаемого материала, без принудительной пачки из 25 карточек после каждого шага.
2. **Лицевая сторона:** один ясный учебный стимул, например `以前`, без ответа и случайных подсказок. После нажатия «Показать ответ» / flip — **обратная сторона** с `yǐqián`, переводом на RU/TJ/UZ и уместным коротким примером `我以前住在这里。` (Wǒ yǐqián zhù zài zhèlǐ. — «Раньше я жил здесь»). Порядок подачи и раскрытие управляются выбранным видом упражнения. Для слов по другим уровням/курсам примеры брать из реального допустимого материала, а не генерировать вымышленные факты.
3. **Быстрые действия:** 🔊 воспроизвести доступную китайскую озвучку по нажатию; после открытия ответа `❌ Повторить` / `✅ Знаю` или эквивалентные ясные локализованные действия; видимый прогресс карточек. Для режимов, где правильность можно проверить автоматически (выбор, сборка, ввод, распознавание), использовать **проверяемый ответ**, не подменять его одной самооценкой.
4. Карточки должны оставаться **короткими, плавными и доступными**: анимация перелистывания необязательна и ненавязчива; поддержать reduced motion, крупный китайский шрифт, правильные тоны pinyin, доступные зоны нажатия, VoiceOver/TalkBack, RU/TJ/UZ, PWA Safari/Home Screen и Android. Не показывать правильный ответ до проверки в активных тестовых режимах.
5. По завершении — **краткий честный итог** (сколько просмотрено, сколько помечено «знаю» / «повторить», что будет повторено) и путь продолжить исходный урок. Карточка/сессия обязаны восстанавливаться/завершаться без потери основного lesson progress; не навязывать бесконечный цикл.

### 2. Интеграция с существующим Adaptive Learning (UIUX-007)

- Выбирать карточки из **фактического** активного урока и выбранной версии/уровня HSK 2.0/3.0. Для персональных повторений приоритет — проверенные `course_mistake_targets`, learning signals и существующий word mastery/SRS; повторяющийся трудный материал может возвращаться в другой подходящей форме, не создавая независимые списки или второй движок карточек.
- **Сильное различие типов доказательств:** `❌`/`✅` после раскрытия карточки — это *self-assessment* («кажется, помню»), а не доказанная ошибка или 100% правильных ответов. Хранить и интерпретировать отдельно от server-verified ответа и подтверждённых ошибок. При необходимости применять это как **мягкий сигнал** для SRS/предложения повторить, а закрепление/ошибка должны подтверждаться настоящим проверочным форматом. Не начислять XP за каждое произвольное ✅ и не менять streak/уровень из-за самооценки.
- `Мои ошибки` — дополнительная самостоятельная точка закрепления; основной автоматический повтор проводится **внутри обычного следующего урока** (UIUX-007). Карточка может быть лёгким вводным этапом перед **реальным проверочным упражнением по тому же навыку** (распознавание иероглифа, pinyin, тон/аудирование, значение, порядок слов, грамматика). Не замещать обязательные три разных формата mastery одной последовательностью самооценок, не считать самооценку подтверждённым исправлением.
- Связать результат с курсом, Practice, Daily Plan и при необходимости AI Voice через **один согласованный learning state**; AI Voice может естественно использовать трудные слова из повторения, но не вести несуществующий «балл» карточек. Обязательная cross-reference в технической реализации: `UIUX-007 / COURSE-ADAPTIVE-001`.
- Сохранить server-authoritative course progress, доступы Free/Trial/Pro, XP dedup, историю ошибок, существующие блокировки/открытие уроков, версии HSK и межплатформенную синхронизацию. Не вмешиваться в формальные экзаменационные оценки.

### 3. Обязательная зависимость от готовой инфраструктуры

- На момент реализации по уточнению владельца **Analytics, Monitoring, Optimization, Smart Render и иные большие проекты будут уже реализованы**. Прочитать их **актуальные рабочие** контракты на новом `main`, переиспользовать существующие компоненты, события, журналы, coverage/CI, кэш, рендеры и состояния загрузки. **Не реализовывать** их заново и не создавать дубликаты сервисов/телеметрии. UI не блокируется при технической ошибке рекомендации/загрузки аудио: корректный fallback на обычный урок.

## UIUX-009 — Глобальная очистка лишних подложек под иконками и вторичными действиями

**Статус:** ✅ ЗАФИКСИРОВАНО ПО ПРЯМОМУ ТРЕБОВАНИЮ ВЛАДЕЛЬЦА (2026-11-12). Это глобальное визуальное правило для PWA и Android. На этапе обсуждения — только план, код не менять.

**Проблема:** в ряде экранов отдельные иконки и вторичные действия (например, шестерёнка/настройки, мелкие tool-actions, отдельные плавающие быстрые действия) лежат на дополнительных круглых/капсульных подложках или мини-карточках, из-за чего интерфейс выглядит перегруженным и менее профессиональным. Появляется ощущение «кнопки на карточке поверх карточки».

### Решение

- Убрать **лишние декоративные подложки / карточки / двойные круги / вторичные рамки** под одиночными иконками и вторичными action-кнопками.
- Сохранить достаточный **tap target** и accessibility area, но визуально сделать action проще: либо чистая иконка, либо лёгкая системная кнопка без ощущения отдельной карточки.
- Для primary CTA (например, `Продолжить`) полноценная кнопочная форма сохраняется. Требование касается прежде всего **избыточных фоновых подложек** у secondary/utility controls.
- Floating action допускается только если он действительно нужен как отдельный приоритетный инструмент; даже тогда избегать эффекта `кнопка внутри ещё одной карточки`.

### Обязательные правила

1. **Одиночная utility-иконка** (settings, info, menu, quick action и т.п.) не должна сидеть на тяжёлой карточке, если это не критично по смыслу.
2. Если нужен фон для контраста, использовать **минимальный, лёгкий и единый стиль**, без двойных обводок, теней и лишних слоёв.
3. На lesson/course/practice/profile экранах избегать повторения паттерна `иконка + отдельная круглая подложка + ещё одна внешняя обводка`.
4. Не убирать интерактивность: сохраниться должны hit area, focus state, press state и доступность для VoiceOver/TalkBack.
5. Проверить на всём приложении consistency: lesson top bar, быстрые действия, mini tools, floating buttons, modal header actions.

### Дизайнерский смысл

Цель — сделать HSK AI визуально чище и дороже: меньше визуального шума, меньше «псевдокарточек», больше воздуха и единообразия. Это особенно важно рядом с уже согласованным `Unified Header System` и общим минималистичным стилем.

### Проверки при приёмке

- На ключевых экранах пропадают лишние подложки под utility icons, но доступность и удобство нажатия не ухудшаются.
- Visual hierarchy улучшается: пользователь быстрее считывает основной контент, а не вторичные контролы.
- Нет регрессии контрастности, press/focus состояний, safe area и поведения на PWA/Android.
- Применение правила единообразно, а не только в одном месте.

## UIUX-010 / FEATURE-SPOTLIGHT-001 — Каталог новых функций и одноразовые in-app показы с реальным переходом

**Статус:** 🟠 НОВОЕ ТРЕБОВАНИЕ ВЛАДЕЛЬЦА ЗАФИКСИРОВАНО (2026-11-13). Схема административной статистики и некоторые UX-решения — **на обсуждении, не считать окончательно утверждёнными**. Плановый аудит only-read; код продукта, Admin PWA и GitHub не менять до отдельного итогового поручения.

**Цель:** демонстрировать пользователям **действительно выпущенные** заметные функции/разделы/крупные улучшения через одно аккуратное центральное окно с фото либо коротким видео, 2–3 строками текста и кнопкой **«Попробовать»**. Кнопка должна открывать **не просто вкладку, а целевую рабочую функцию**, если она доступна пользователю. Управление, медиа, on/off и статистика — в действующей Admin PWA.

### 1. Факты текущего GitHub `main` (проверено 2026-11-13, SHA `1eb14684bd11a7275907d187e22d03227cff2bab`)

- `app/admin_api/pwa_campaigns.py`, `app/static/admin-pwa/app.js`: уже есть **release-кампании**, языковые копии RU/TJ/UZ, отдельные аудитории и Admin UI; это прежде всего механизм outbound-кампаний, а **не готовая система центральных in-app popup**. Нельзя объявлять готовым то, чего ещё нет.
- `app/admin_api/pwa_campaign_assets.py`: имеется ограниченная загрузка/валидация изображений и видео для кампаний. Переиспользовать пригодные проверки/хранение лишь после проверки клиентской доступности, доступа, срока жизни, формата и CDN; не считать Telegram `provider_file_id` готовым публичным URL.
- `android/.../core/navigation/DeepLinkRouter.kt`: есть строгий разрешённый список внутренних переходов (`course`, `lesson`, `voice`, `practice`, `profile`, `subscription`, и др.), и прямо сказано: deep link **не предоставляет entitlement**.
- `app/static/course_v3_data/iphone-pwa-inline-pro.js` и `.../iphone-pwa-inline-pro-bridge.js`: есть действующий встроенный Pro checkout с серверными ценами, кнопками «Получить Pro»/«Другие тарифы» и восстановлением оплаты. **Не строить второй payment engine.**
- `app/db/models/release_feedback.py`: есть отдельный Telegram-oriented учёт доставки, перехода «try» и сбора отзывов — он не заменяет per-platform, per-announcement in-app impressions и подтверждённую активацию функции.

### 2. Центр экрана и сценарии

- Рендер: **один центральный модальный слой** поверх активного приложения, в стилистике HSK AI: одна фотообложка **или** короткий видеоролик, локализованный заголовок, краткое описание максимум 2–3 строки, один главный CTA **«Попробовать»**, спокойное закрытие ✕. Не копировать существующую тяжёлую рекламную карточку и не накладывать несколько modal/paywall одновременно.
- Видео: небольшой безопасный файл с постером, ограниченным размером/длительностью и fallback на фото/постер; **без принудительного звука**, учитывать reduced motion, сетевые условия и доступность. UI не ждёт загрузки видео для запуска курса.
- **Условие показа:** экран не должен прерывать урок, текущий ответ/тест, AI Voice, ввод текста, оплату, логин, onboarding, синхронизацию и критические системные диалоги. Только при безопасном входе/возврате в приложение, с ограничением **не более одной** новой карточки за один вход; несколько релизов образуют очередь по приоритету, а не пачку popup.
- Избранная карточка должна быть уже опубликована, соответствовать поддерживаемой версии приложения/feature flag/платформе и иметь подтверждённый работающий маршрут. Не показывать CTA на «Скоро», отключённую или неготовую функцию.
- После закрытия ✕ или Try — по умолчанию повторно **автоматически** не показывать то же объявление на данной логической платформе; при желании оставить просмотр из «Что нового» в настройках, без нового popup. Не подменять одноразовый показ локальным `localStorage` без server-account истории.

### 3. Главное правило: «Попробовать» должно действительно работать

- У каждого объявления — стабильные `announcement_id` + `feature_id` + **зарегистрированный typed destination/action**, например `practice.mistakes`, `course.current_lesson`, `voice`, `feature.new-screen`. **Не принимать произвольный внешний URL / код / SQL / JS / deep-link из редактора Admin.** Список реально доступных действий регистрируется разработчиком в коде и валидируется сервером; админ выбирает из каталога, а не вводит непроверенный адрес.
- Для PWA и Android — **разные проверенные destination mapping** с одинаковой семантикой. Android: существующий allowlisted `DeepLinkRouter` и native navigation; PWA: существующие app routers/deep-link bridges. Переход до точной функции, не в произвольную главную вкладку; сервер проверяет account, подписку, rollout, доступность контента и актуальный прогресс.
- Непосредственно перед переходом проверить доступ. При `trial`/`pro` и разрешённом feature access — **реально запустить целевую функцию**, не просто открыть заголовок. При `free`, **если функция требует Pro**, внутри **того же окна** заменить информационный экран на компактный **Pro paywall** с CTA **«Получить Pro»** и **«Другие тарифы»**, используя существующие серверные тарифы/checkout; дать путь назад к анонсу. Если функция **бесплатная**, Free тоже должен попасть в неё: запрещено притворяться, что любой анонс требует Pro.
- `trial` может пробовать только функции, которые действующий серверный entitlement действительно разрешает. Нельзя делать глобальную «trial = pro» проверку клиентом и обходить существующие лимиты. Для `Pro` действуют обычные feature flags и версии. Все реальные ограничения проверяются сервером.
- **Единый слой модалки:** не открывать одновременно рекламный popup и отдельный modal paywall поверх него. Использовать существующую checkout-бизнес-логику/обработку платежа; при необходимости встраивать её presentation в тот же контейнер, не дублируя платежные API, план/скидки и purchase state. После успешно подтверждённого платежа — по возможности возобновить **тот самый intended destination** с повторной проверкой прав.
- Ошибка/устаревшая версия/недоступный route: понятный локализованный fallback «Функция пока недоступна», возможность закрыть/попробовать позже; не засчитывать `feature_used` и не выдавать ложно успешный Try. Все действия idempotent и не блокируют основной app flow.

### 4. Один показ — **на аккаунт, на объявление, на платформу**

- Ключ: `(canonical_user_id, announcement_id, logical_platform)`, где **`android`** объединяет Play + Direct и устройства одного user; **`pwa`** объединяет Safari/browser/Home Screen PWA одного user. Если на Android объявление уже показано, **на PWA оно ещё может показаться ровно один раз** — как прямо потребовал владелец; второе Android-устройство не даёт нового показа. Если понадобится более тонкая разбивка iPhone PWA/browser PWA — обсуждается отдельно, не придумывать дополнительные каналы.
- Считать показ только после фактического появления центрального окна, а не по `GET`/предзагрузке/резервированию картинки. Подтверждение impression — authenticated, bounded, idempotent; защита от гонок между сессиями и повторных API-запросов. Если ack недоступен, не зависать/не блокировать приложение, но не выдавать фиктивный показ.
- На каждом `announcement_id` независимая история: просмотр одного релиза **не скрывает будущий релиз**. Учитывать account switch, blocked/deleted accounts, retention, logout, reinstall, offline и миграцию аккаунтов.

### 5. Admin PWA: единый каталог «Обновления / Feature Spotlight»

- Каталог с `Draft / Ready / Active / Paused / Archived` (при необходимости сократить без потери безопасности); создать/редактировать, превью по платформе и RU/TJ/UZ, загрузить фото/видео, включить/выключить, указать аудиторию (в т.ч. `free / trial / pro`), приоритет, время начала/окончания, поддерживаемые версии и платформы, назначить **существующий зарегистрированный action**.
- Публикацию/активацию выполняет админ (через текущий Admin PWA auth/audit/confirmation). **Codex при добавлении новой крупной функции обязан создать/обновить запись в программном feature registry, привязать и проверить точный Android + PWA маршрут и сгенерировать Draft в каталоге, но не включать показ автоматически.** Если маршрут одной платформы ещё не реализован, она выключена для анонса; нельзя давать неработающий Try.
- Никакой второй административной панели, второго редактора картинок, отдельного медиапровайдера или нового сервиса рассылки без доказанной необходимости. In-app анонсы **не являются Telegram push/broadcast** и не должны повторно рассылать сообщения.

### 6. Admin PWA: статистика — ПРОЕКТ ДЛЯ ОБСУЖДЕНИЯ

Статистику выводить **для каждой карточки** (и компактно по всему каталогу), с фильтрами `период / logical platform (Android, PWA) / verified access status (Free, Trial, Pro)`; считать по **уникальным подтверждённым аккаунтам**, с явными знаменателями; попытки/повторы — отдельным диагностическим счётчиком.

**3 основные метрики:**
1. **Показы (impressions)** = число уникальных `(account, announcement, platform)` с подтверждённым отображением центрального окна. Не равно eligible аудитории или API fetch.
2. **Try CTR** = уникальные пользователи, нажавшие «Попробовать», / уникальные пользователи, увидевшие окно, в той же платформе/периоде/когорте. При фильтрации периода показать, когда когорты несовместимы, не выдавать неинтерпретируемую конверсию.
3. **Реальная активация функции** = уникальные пользователи с подтверждённым entry + **значимым первым действием** в указанной функции, / увидевшие окно. Для каждой feature action заранее обозначить, что именно значит успешная активация; один маршрут/открытый экран сам по себе не равен полезному использованию. Если activation writer отсутствует — `not_instrumented`, а не вымышленный 0.

**Диагностика и Pro-воронка (без избыточного отдельного дашборда):** закрыли ✕, Try → Pro paywall, выбрали «Получить Pro»/«Другие тарифы», начали checkout, **сервером подтверждённая** оплата, успешное возвращение в target; ошибки маршрута/entitlement/media и недоступный канал. Считать checkout/payment attribution только по реальному source/attempt, а не по временной близости. Никогда не считать клик оплатой. Никаких «доставлено 100%», если видимость неизвестна.

**Ограничители:** popup exit/dismiss, частота непрошеных окон, time-to-open target, частота отказа маршрута, перформанс и корректность paywall; отслеживать только минимально необходимые события, без сырого пользовательского контента. Согласовать с **действующей** Analytics Integrity registry/Admin read projections и Monitoring Impact; обычный dismiss — маркетинговое действие, а не системный incident.

### 6A. Feature Performance & Health — единый Analytics + Monitoring для каждого анонса (предложение для согласования)

**Статус:** ✅ ОДОБРЕНО ВЛАДЕЛЬЦЕМ (2026-11-13) **УСЛОВНО, С ОБЯЗАТЕЛЬНЫМ ПОВТОРНЫМ АУДИТОМ ПОСЛЕ РЕАЛИЗАЦИИ ОБЩЕГО MONITORING**. Одобрен принцип отображения Analytics + Monitoring внутри карточки каждой новости (без отдельного мониторинга и второго Admin dashboard). Конкретный набор полей, порогов и привязки событий нельзя окончательно фиксировать до сверки с фактически работающим Monitoring/Analytics на актуальном `main`. Переиспользовать существующий Admin Inbox, incident pipeline, Apple Push, coverage/CI и аналитические цепочки.

**Админский UX:** в каждой карточке каталога «Обновления» один компактный раздел **Feature Performance & Health**: (а) маркетинговые показатели из §6 (показы, Try CTR, подтверждённая активация), (б) техническая работоспособность. В списке каталога — только `нормально / проблема / данных недостаточно` и вход в подробности. Не заявлять `0 ошибок`, если сигналы отсутствуют или неполны.

**Сквозной контракт:** `popup actually shown → try_clicked → server entitlement decision → expected paywall OR verified exact target_ready → feature's meaningful first-use`. Связать события через `announcement_id`, `feature_id`, `platform`, `app_build`, и безопасный correlation/attempt ref, с canonical authenticated user и дедупликацией. `try_clicked` НЕ значит, что маршрут работает. Для Free с закрытым Pro-доступом ожидаемый paywall — **корректный исход**, не техническая ошибка; обычный отказ, отказ от оплаты, отсутствие подписки, офлайн и самостоятельное закрытие — не crash.

**Минимальные технические показатели:**
- **Try → рабочая функция:** число и доля проверенно успешных `target_ready` среди авторизованных попыток, отдельно `expected_paywall` и реальные отказы. Для «реально использовал» — отдельно проверенное первое действие. Если writer отсутствует, вывести `not_instrumented`, а не фиктивный успех.
- **Incidents / affected accounts:** дедуплицированные технические случаи и уникальные затронутые аккаунты; breakdown по Android/PWA, версиям, feature/announcement, first/last seen, severity; использовать только корректно наблюдаемые факты.
- **Latency / performance:** задержка до готовности точного target и частота таймаутов, если эти наблюдения доступны в действующей performance-инфраструктуре. Медиа/постер не должны блокировать first render.

**Отслеживаемые сбои:** неправильный или отсутствующий deep link/action registry; неоткрывающийся/неуспешный target; неработающий Pro переход после Try; неверный access/entitlement mapping; подтверждённый backend 5xx или JS/Kotlin crash; повторяющийся сбой медиа без fallback; возврат после оплаты не в исходную функцию. Не писать повторный incident основной функции лишь потому, что туда перешли из Spotlight; linking to existing owner/incident.

**Админские действия:** из карточки новости переходить к **уже существующему Admin Inbox** с нужным фильтром и безопасным error code. Важные новые/усугубившиеся проблемы — существующий Apple Push только по серверной severity, дедуп, cooldown, rate-limit; никаких push за каждый технический event. В редакторе — **«Приостановить показ»** только данной кампании; отключать весь продукт/обучение/checkout запрещено. Автоматическую остановку без достоверной массовой аномалии и защищённых порогов не вводить; отдельное согласование.

**До публикации:** Admin Preview + проверенный тестовый Try на каждой разрешённой платформе и Free/Trial/Pro; проверить точный route, его `target_ready`, server access/paywall, видео/фото fallback, возврат после подтверждённой оплаты. При отсутствии рабочего маршрута блокировать публикацию на соответствующей платформе. В CI обязателен корректный `Analytics Impact` и `Monitoring Impact` с E2E: event→сохранился→верный Admin consumer/Inbox, не просто mock/enum. Ошибка Monitoring не блокирует учебный процесс; без личных ответов, голоса, токенов, платёжных данных и сырых URL в логах.

**Ключевое ограничение:** Monitoring **обнаруживает** проблему и ускоряет расследование; он **не исправляет автоматически** код. Технические фиксы проходят нормальные тесты и deployment. Рекомендуемые пороги алертов установить после первого измеренного baseline, а не выдумывать заранее.

## UIUX-011 — AI Voice Hybrid Orb: фирменный Red Orb + анимационные паттерны Thinking Orbs

## UIUX-012 — Checkout Exit Offer: центральное предложение скидки 20%, двойной X и сохранение checkout

**Статус:** ✅ УТВЕРЖДЁННЫЙ ВЛАДЕЛЬЦЕМ UX-СЦЕНАРИЙ (2026-11-13); **только планирование, не реализовывать сейчас**. В будущий общий Codex handoff включить вместе с остальными UI/UX задачами. Цель — не терять пользователя, дошедшего до оформления оплаты, при этом оставить ясный и рабочий выход без ловушек.

### 1. Утверждённое поведение

1. **Контекст:** пользователь находится в разделе подписки/checkout; прежде всего важен сценарий, где уже выбран тариф/метод или открыты реквизиты/QR. Правило работает на соответствующих PWA и Android checkout-поверхностях; системный Back / обычная стрелка «Назад» продолжает возвращать на **один реальный предыдущий шаг**, сохраняя выборы. Крестик `X` — закрытие checkout, а не замаскированное пошаговое Back.
2. **Первое нажатие на `X` при eligibility:** вместо немедленного выхода показать **один компактный блок по центру экрана** (modal/overlay) с явным заголовком про **скидку 20%**. Внутри ровно одно главное действие **«Воспользоваться скидкой 20%»** и один `X` для закрытия самого предложения. Не добавлять вторую кнопку «Выйти», длинный маркетинговый текст, обязательное объяснение или отдельный экран.
3. **Нажатие «Воспользоваться скидкой»:** отправить существующему авторитетному серверному механизму принятие offer; **только при подтверждённом сервером успехе активировать скидку −20%** в текущем checkout, обновить реальную цену и условия оплаты на основе серверного quote, затем убрать центральный блок. Пользователь **остаётся в checkout на прежнем шаге** с актуальным тарифом, методом и реквизитами, если они действительны. При ошибке применения показать короткий inline error/retry; не заявлять, что скидка включена, до подтверждения.
4. **Нажатие `X` внутри предложения:** закрыть **только центральный блок**, оставить пользователя в том же разделе подписки, на том же шаге, с сохранёнными выборами. Не закрывать checkout, не открывать новое предложение и не менять цену.
5. **Следующее нажатие `X` checkout после отказа:** **выйти из раздела подписки сразу**, без повторного показа скидки, без дополнительного подтверждения и без возвращения через все предыдущие этапы. Внутри одного checkout-attempt предложение показывается не более одного раза. При новом самостоятельном открытии checkout можно снова предложить скидку, если пользователь всё ещё имеет право на неё.
6. **Если пользователь уже активировал скидку:** не показывать ещё одно exit-offer поверх уже применённой скидки в этом же checkout. При дальнейшем закрытии должен существовать честный, прямой выход. Действительное серверное платёжное состояние (созданный инвойс/ожидание подтверждения/ручная проверка) не сбрасывать и не подменять новой попыткой оплаты.
7. **При отсутствии права на предложение:** `X` выходит из checkout по обычному пути, без ложной скидки и без искусственных задержек. За пределами этого исключения избегать двойных/стековых popups, exit loops, наигранных дедлайнов и скрытых способов выхода.

### 2. Eligibility — точное условие владельца

Владелец указал: предлагать 20% **всегда, пока пользователь ещё ни разу не оформлял подписку ИЛИ ни разу не использовал скидку**. В спецификации это **логическое OR**: `never_had_paid_subscription OR never_redeemed_any_discount`. Не подменять его автоматически более строгим `AND` или правилом «только новые пользователи». Оба признака вычисляются **на сервере по подтверждённой истории платежей/скидок** для canonical account, а не по локальному флагу UI, полю `current Pro` или одному когда-то показанному offer.

- Пользователь **никогда не покупал Pro** → eligible, если checkout вообще доступен.
- Пользователь **раньше покупал Pro, но ни разу не применял скидку при подтверждённой оплате** → eligible по второй части условия, когда checkout снова доступен.
- Пользователь **и раньше платил, и уже воспользовался скидкой при подтверждённой оплате** → not eligible.
- Активный Pro, заблокированный аккаунт, недоступный checkout, отсутствующий актуальный 20% promo или уже pending/выполненный платёж не должны приводить к новому неподходящему invoice/платёжному запросу; действующие бизнес-ограничения проверяются отдельно.
- **«Воспользовался скидкой»** означает подтверждённое сервером использование скидки **при состоявшейся оплате**, а не просмотр popup, его отклонение или даже один клик по CTA без завершённой транзакции. Историю всех реально использованных типов скидок учитывать без ошибочных повторов, refund/reversal — по действующим правилам платежей.
- Показывать предложение **на новом допустимом checkout-attempt**, даже если в предыдущей попытке пользователь закрыл его; сам факт `view` / `X` / истёкшего UI-срока не должен навсегда лишать права на повторный показ. Не создавать бесконечный показ при втором `X` **в том же attempt**.

**Важная экономическая проверка:** условие `OR` позволяет предложить скидку бывшему платившему пользователю без истории скидок. Это намеренный буквальный смысл указания, а не критерий «только первая оплата». До реализации проверить влияние на доход/возврат клиентов и убедиться, что owner не имел в виду `AND`; без его явного решения автоматически не ужесточать eligibility.

### 3. Центральный блок и визуальный стиль

- Центр viewport/видимой области; компактная, адаптивная ширина, нормальные safe areas, корректное центрирование при открытой клавиатуре и на маленьких экранах.
- Минимальный контент: **«Скидка 20%»**, одно короткое пояснение при необходимости, primary CTA **«Воспользоваться скидкой»**, маленький `X` справа вверху. Все тексты локализуются на **RU / TJ / UZ**, не хардкодить русский текст на всех языках.
- Скидка не применяется только от просмотра блока. Цена **до → после** и итоговая валюта/срок должны оставаться точными; серверный тариф/quote является источником истины. Если доступен продлеваемый тариф, прозрачно показать, на что именно распространяется скидка и последующие платежи.
- Один overlay в один момент: не наслаивать этот блок поверх Lava provider offer, QR preview, другого paywall, permission/system sheets или checkout подтверждения. Все фоновые действия внутри checkout контролируются нормально; обычный `X` не теряет пользовательские выборы.
- Accessibility: focus/Back/Escape, озвучивание `X`/CTA, контраст, touch target, reduced motion. Не использовать агрессивный таймер, fake «скидка истекает» или forced countdown для удержания.

### 4. Факты по текущему коду и минимальная интеграция (read-only, 2026-11-13; перепроверить актуальный main перед реализацией)

- **PWA:** `app/static/course_v3_data/iphone-pwa-inline-pro-bridge.js` встраивает checkout и превращает `#pwaCheckoutBackBtn` в `X`, который может вызвать `returnToCourseFromCheckout()` сразу. Поэтому этот UX требует изменить **только обработку закрытия** и его presentation, сохранив истинный шаговый Back и существующую navigation/checkout модель; не заменять checkout новой реализацией.
- **Android Direct manual:** `android/app/src/direct/java/com/pomp/hskai/feature/subscription/SubscriptionCheckoutHost.kt` уже ведёт native Back по шагам (`model.back()`), а верхний `X` вызывает `onClose()` напрямую. Согласовать именно этот разрыв, сохранив checkout ViewModel и системное Back-поведение.
- **Android Lava:** `android/app/src/direct/java/com/pomp/hskai/feature/subscription/LavaCheckoutViewModel.kt` уже имеет `requestProviderClose()` и условный `exitOffer(view/claim)`. `NativeLavaCheckout.kt` показывает существующий диалог с предложением/отменой. **Не строить второй промо-механизм** и не наслаивать ещё один retention-modal; адаптировать/переиспользовать существующий.
- **Сервер:** `app/services/pwa_exit_offer_service.py` использует `EXIT_PERCENT = 20`, модель `PwaExitOffer`, `offered_at`, `accepted_at`, `consumed_at` и сейчас 24-часовой `EXIT_TTL`; `_capable()` проверяет доступность Lava promo и текущие ограничения, **но не реализует полностью требуемую историческую формулу eligibility OR**. Изменение «предлагать повторно на новом checkout-attempt, пока eligible» потребует пересмотра TTL/одноразового consumed состояния, **без выдачи повторно использованной скидки** и без клиентского обхода платежных проверок.
- **Lava/цены:** `app/services/lava/checkout.py` уже обрабатывает `exit_discount` и серверный 20% promo mapping. Проверить реальное назначение скидки через существующие state/quote/checkout API, отсутствие комбинирования несовместимых скидок, консистентность суммы invoice и webhook/ledger. Не считать click подтверждённой оплатой.
- **Play channel:** не добавлять запрещённую in-app покупку; направлять покупку через разрешённый существующий PWA путь. Единая UX-семантика применяется на фактически поддерживаемых checkout-поверхностях.

### 5. Состояния и критерии приёмки

1. Eligible → первый `X` → **один центральный 20% блок**; checkout и выбранный шаг не исчезли.
2. В блоке ровно один CTA принятия + один `X`. `X` блока → только закрыть блок → остаться в checkout; второй `X` checkout → выйти без повторения offer.
3. CTA → серверное принятие → реальный quote уменьшен ровно на **20% по правилам округления действующего платёжного провайдера**, отображены корректные сумма/валюта/срок; пользователь остаётся в своём шаге. Error/offline/timeout не подтверждают скидку ложно; retry не создаёт дубликат invoice.
4. Обычный Back/Android system Back/браузерная навигация → один шаг назад; preview/sheet закрывается раньше основной checkout-навигации. После закрытия/reopen восстановлены только безопасные и действительные выборы.
5. Не eligible / уже использовал предложение на данном attempt / accepted discount / активный Pro или pending payment → нет повторного неподходящего popup и неожиданных лишних списаний.
6. Eligibility OR проверена матрицей: never paid + never discounted; paid + never discounted; never paid + discounted; paid + discounted; разные источники скидок, user switch и несколько устройств. Серверная дедупликация и account ownership обязательны.
7. Проверить PWA Safari/Home Screen, Android Direct, Play→PWA, RU/TJ/UZ, малые экраны, keyboard, reduced-motion, backend/Lava failures, многократный `X`, pending/manual review, logout/account switch; не ломать Pro, возврат в урок или существующие checkout-потоки.
8. Аналитика для будущей оценки (после сверки с готовыми Analytics/Monitoring): `offer_displayed`, `offer_accepted`, `offer_dismissed`, `checkout_exited`, **подтверждённая оплата с применённой скидкой**. Дедупликация по account/attempt; не создавать второй event pipeline и не считать показ оплатой.

**Приоритет при реализации:** это **конкретное согласованное требование** к экрану обуны/checkout. При расхождении с общей формулировкой `hsk-ai-ui` Skill §18 («Continue payment / Exit checkout») **применить этот согласованный сценарий 20% offer + CTA + X, затем свободный выход**; перед реализацией синхронизировать общее правило с утверждённым сценарием, чтобы у Codex не оставалось противоречивых инструкций. До общего handoff product code и общие правила не менять.
