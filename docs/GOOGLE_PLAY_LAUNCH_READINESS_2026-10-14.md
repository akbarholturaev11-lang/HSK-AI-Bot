## Critical blocker 1 — preserve APK -> Play update continuity

The first Play App Signing enrollment must use the EXISTING `direct`
app-signing key, not a brand-new Google-generated signing key.

- The release keystore is private; retrieve it on the owner's trusted
  computer or from the secure backup. **Never paste the keystore, private
  key, key password, or PEPK output into a chat or repository.**
- `.github/workflows/android-release.yml` pins the existing direct APK
  certificate. The manual Play preflight verifies the same key in its
  Play APK, direct APK and Play AAB.
- In Play Console's **App signing** setup, explicitly choose to provide
  your own app-signing key and complete Google's secure export/import.
  Do not accept Google's autogenerated app-signing key by default.
- After enrollment, compare **App signing key certificate** SHA-256 in
  Play Console to a known-good existing direct APK, not merely to the
  **Upload key certificate**. They are separate concepts.
- A separate future **upload key** is recommended: Google will accept AABs
  signed by that upload key and re-sign downloaded APKs with the original
  app-signing key. At that point update this initial-preflight workflow's AAB
  upload-key check deliberately; do NOT change the direct APK signing key.
- Keep `applicationId` unchanged and use increasing `versionCode` values
  for both channels. Test an existing signed direct installation -> Play
  installation/update with a tester before general availability.

## Account deletion independent of Telegram — implemented, release verification pending

The 2026-10-15 patch removes the Telegram-only request dependency:
- Android Profile / Security prepares a deletion challenge with the existing
  authenticated session and submits only after explicit in-app confirmation.
- `/account-deletion` provides public Google, Apple and Telegram ownership
  verification, explicit confirmation, a durable receipt and status checking.
- Google/Apple callbacks resolve only an existing `(provider, subject HMAC)`;
  they never create/link an account, match email or issue login tokens.
- Requests use internal `users.id`; cleanup supports accounts with no Telegram
  ID without migrating or changing existing sign-in/account-creation rules.
- Submitted requests remain in the operator queue until processed. The target
  is 30 days; existing approved-payment/accounting retention is preserved.

Deploy the backend/schema and updated Android builds before marking the live
requirement complete. Run the Google/Apple/Telegram live checklist and operate
the deletion queue as described in `docs/ACCOUNT_DELETION_OPERATIONS.md`.
Apple is offered only when its existing credentials are configured; Google
web verification requires the existing desktop/web OAuth credentials. Reuse
the already registered native OAuth callback URLs; no new redirect is needed.

Regression coverage exercises provider-only accounts, native and public proof,
browser binding, expired/tampered/replayed proof, duplicate requests, durable
acknowledgment, operator cleanup and financial retention, plus mobile web and
both Android flavors. A static URL returning 200 is insufficient release proof.

## Monetization decision before Play submission (extensible architecture)

**Today the Play variant is consumption-only, not permanently free-only.**
Users can access server-unlocked lessons, but cannot purchase Pro or HSK 3.0
inside the current Play APK. This is an interim release choice.

**Later, Play can have its own Google Play Billing subscriptions and one-off
HSK 3.0 unlock**, without changing the existing bank/card/manual checkout
used by `direct` or Telegram. Keep payment providers separate:

| Distribution | Purchase UI and payment | Access on successful payment |
| --- | --- | --- |
| `direct` APK / site | Existing HSK AI backend checkout | Shared backend entitlement |
| `play` APK (current) | Consumption-only, no in-app purchase | Read shared backend entitlement |
| `play` APK (future) | Google Play Billing Library | Server-verified shared backend entitlement |

**Architecture and future change contract**:

1. `android/app/src/direct/...` remains the direct checkout host.
   `android/app/src/play/...` contains its **own** checkout host and limit
   gate. They share *signatures and entitlement results*, not payment UI.
2. Replace `src/play/.../SubscriptionCheckoutHost.kt`'s temporary no-op
   with native Play Billing product selection, purchase handling and status UI
   when that phase is approved. Update `src/play/.../LimitGateHost.kt`
   accordingly; **do not modify the direct checkout**.
3. Verify Play purchase tokens **server-side** using Google's API and only
   then grant/renew/revoke `Pro` and HSK 3.0 access through the existing
   shared user entitlement service. Record purchase origin to reconcile
   renewals, cancellation, refunds and duplicate grants.
4. Implement acknowledgments, pending purchases, subscription status
   transitions, subscription-management deep links and restore purchases.
   Avoid charging again for entitlements already provided elsewhere.
5. No external direct checkout or payment steering in the Play build unless
   specifically allowed under an applicable, verified Google program.
   Do not share `direct`'s billing view model with Play.

**CI compatibility:** `android/tools/check_play_release_contract.py`
guards package identity, release signing, direct/Play separation and
install/update permissions; it intentionally does **not** require Play
checkout to remain a no-op or `canSubscribe = false`. Thus adding Google
Play Billing later does not require disabling safety checks.

The consumption-only first release has a conversion cost. Decide when
Google Play Billing should launch **before** publishing. Nothing in this
preflight adds billing or changes existing payment flows.

Docs:
https://support.google.com/googleplay/android-developer/answer/10281818
https://developer.android.com/google/play/billing/integrate

## Manual, non-publishing CI preflight

After this workflow lands on `main`:

1. GitHub Actions -> **Android Play preflight** -> Run workflow.
2. It reads the existing signing key from GitHub Actions secrets, builds
   signed direct and Play APKs plus the Play AAB, verifies package identity,
   certificate continuity and absence of Play self-install permissions.
3. Download `hsk-ai-play-preflight-aab` from the workflow artifact if it passes.
4. **Do not submit until the blockers above are resolved and the developer
   account is approved.** Upload the AAB manually into the appropriate Play
   Console testing track; the workflow does not publish it.
5. Compare Google Play's actual **App signing key** certificate SHA-256 with
   the pre-existing direct app signing certificate before proceeding.

Reminder: A successful CI check proves only these technical conditions,
not compliance with every Play policy or a Google review approval.
