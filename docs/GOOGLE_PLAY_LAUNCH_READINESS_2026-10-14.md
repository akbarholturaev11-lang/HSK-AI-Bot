# Google Play launch readiness — HSK AI (2026-10-14)

Status: PREPARATION. Google identity-verification submission is under review;
this is not developer-account approval or app approval. No Play Console
submission, signed production rollout, or billing change is performed by this
document.

## Verified in the repository

- Android `applicationId`: `com.pomp.hskai`; version: `1.7.13`,
  `versionCode=44` at audit time. Increase versionCode before the next release.
- `direct`: sideload APK, checkout and user-confirmed APK updater.
- `play`: no external checkout or APK install permission, access status
  synchronized through the same backend, no self-updater.
- Signed direct release workflow pins the release certificate SHA-256 and
  refuses to publish an APK signed by a different key.
- Privacy and account-deletion web routes exist at `/privacy` and
  `/account-deletion`; Android links to both from Profile / Security.

## Critical blocker 1 — preserve APK -> Play update continuity

The first Play App Signing enrollment must use the EXISTING `direct`
app-signing key, not a brand-new Google-generated signing key.

- The release keystore is private; retrieve it on the owner's trusted
  computer or from the secure backup. **Never paste the keystore, private
  key, key password, or PEPK output into a chat or repository.**
- `.github/workflows/android-release.yml` pins the existing direct APK
  certificate. The manual Play preflight verifies the same key in its
  Play APK, direct APK and Play AAB.
- In Play Console's **App signing** setup, explicitly choose to provide
  your own app-signing key and complete Google's secure export/import.
  Do not accept Google's autogenerated app-signing key by default.
- After enrollment, compare **App signing key certificate** SHA-256 in
  Play Console to a known-good existing direct APK, not merely to the
  **Upload key certificate**. They are separate concepts.
- A separate future **upload key** is recommended: Google will accept AABs
  signed by that upload key and re-sign downloaded APKs with the original
  app-signing key. At that point update this initial-preflight workflow's AAB
  upload-key check deliberately; do NOT change the direct APK signing key.
- Keep `applicationId` unchanged and use increasing `versionCode` values
  for both channels. Test an existing signed direct installation -> Play
  installation/update with a tester before general availability.

Docs:
https://developer.android.com/studio/publish/app-signing

## Critical blocker 2 — account deletion independent of Telegram

The Android profile opens `/account-deletion`, which currently instructs the
user to submit a request through a **linked Telegram account**. Google/Apple
users without a linked Telegram account may be unable to use that path.

Before production, implement and test a request flow that works with ANY
HSK AI account identity (Telegram, Google, or Apple), including:
- an authenticated in-app deletion request or verified-account flow;
- an external, publicly accessible web route to request deletion;
- user ownership verification and timely deletion of shared account data;
- documented exceptional retention, confirmation and operational handling.

Do not claim this requirement is complete because a static URL returns 200.
Google Play requires both in-app and external account-deletion options for apps
offering account creation.

Docs:
https://support.google.com/googleplay/android-developer/answer/13327111

## Monetization decision before Play submission

**Current Play variant is consumption-only.** Users can log in and consume
content already unlocked via the shared backend, but cannot purchase Pro or
HSK 3.0 in this Play build.

For paid conversion inside a Play-installed app, implement a policy-compliant
Google Play Billing product and subscription flow (or confirm an eligible
alternative billing program), with server-side purchase verification,
acknowledgment, state transitions, cancellations, renewals and refunds.
Do not silently route Play users to the direct APK's checkout or Telegram
payment pages. Review any support and profile links which could indirectly
lead to checkout.

A consumption-only first release is permitted by Google's payments guidance.
It has a conversion cost: Play users cannot buy from within the app.
The choice must be explicit before publishing.

Docs:
https://support.google.com/googleplay/android-developer/answer/10281818
https://developer.android.com/google/play/billing/integrate

## Manual, non-publishing CI preflight

After this workflow lands on `main`:

1. GitHub Actions -> **Android Play preflight** -> Run workflow.
2. It reads the existing signing key from GitHub Actions secrets, builds
   signed direct and Play APKs plus the Play AAB, verifies package identity,
   certificate continuity and absence of Play self-install permissions.
3. Download `hsk-ai-play-preflight-aab` from the workflow artifact if it passes.
4. **Do not submit until the blockers above are resolved and the developer
   account is approved.** Upload the AAB manually into the appropriate Play
   Console testing track; the workflow does not publish it.
5. Compare Google Play's actual **App signing key** certificate SHA-256 with
   the pre-existing direct app signing certificate before proceeding.

Reminder: A successful CI check proves only these technical conditions,
not compliance with every Play policy or a Google review approval.
