## Event → storage → Admin chain

- Onboarding continues through `CourseMiniAppOnboardingService` → existing `CourseMiniAppEvent(onboarding_completed)` with `users.id`, primary/multi choices and `activation_variant=native_li_v1` → existing Admin learning projection. No fabricated guest-view/success denominator.
- Native provider overview writes existing `SubscriptionEntryEvent` using allowlisted `android_*` origin. A real provider invoice writes generic `ConversionFunnelEvent(checkout_opened)` with `transport=android`; it does **not** impersonate `pwa_pro_*` events. Invoice `source=android` → shared verified `review_locked_payment` → `Payment(payment_method=lava)` / subscription/financial facts → existing Admin finance/Lava/source aggregation. Pending/click/browser return are not approved revenue.
- Feedback: actual stored lesson/foundation/recent activity (or owned used native Voice session) → shared locked `BotFeedback` row → canonical original answers and `finish_feedback` → existing Admin inbox/feedback analytics. Optional Admin transport runs after commit. Paid/free mismatch preserves pending answers; repeat submit cannot regrant a reward. Native prompts do not invent browser activity events.
