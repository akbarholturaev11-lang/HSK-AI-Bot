# Native parity: independent reads and authoritative checkout

- Cause: Profile awaited optional trial metadata before settling its successful primary read; native onboarding had no DTO path for the canonical optional choices; provider checkout had no native transport.
- Fix: settle profile/trial independently with generation/cancellation fences; reuse canonical onboarding/feedback/Lava services and a separate OFF native onboarding switch. A native provider response-loss requires a canonical pending read, while uncertain provider creation remains blocked for review.
- Risk: a browser return, UI choice, capability header or timeout is not proof of identity/payment/access. Pending feedback can outlive a paid/free state change; never overwrite its original answer to make a new questionnaire fit.
- Checkout reopen regression: a session-reused provider model could render its old manual fallback before launching the next read, mounting/loading the manual host twice. Use a disposed host-owned provider ViewModelStore; keep the existing exact overview-count assertion in `SubscriptionCheckoutHostTest.reopeningProAndHskCheckoutInOneSessionKeepsTheRequestedProduct`.
- Prevention: `ProfileViewModelTest`, `OnboardingViewModelTest`, `LavaCheckoutViewModelTest`, `NativeLavaCheckoutTest`, `ActivityFeedbackViewModelTest`, `tests/test_android_lava_checkout.py`, `tests/test_android_activity_feedback.py` and existing PWA/Lava ownership/refund tests. Keep native/public counters separate from actual approved financial records. Source/fixture checks are not real-device/provider release acceptance.
