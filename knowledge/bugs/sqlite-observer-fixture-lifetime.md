# Optional observer cancellation must not destroy its test database

- Cause: the Android analysis observer fixture used one in-memory SQLite connection. A real optional-capture timeout invalidated that connection on the busy CI runner; the replacement connection had no smart_reminder_jobs table. The retention case then failed before its assertions. PostgreSQL keeps its database across connections.
- Fix: the affected SQLite Android observer and Return Analysis fixtures use owned temporary files, passed through the existing nested analysis/backfill setup. Dispose the engine before deleting the directory. Other fixtures keep their defaults. Retention arranges its analysis facts with the actual idempotent capture service before advancing time, so it does not depend on an optional HTTP callback always finishing within the unchanged deadline.
- Risk: test storage only. Production schema, observer timeouts, cancellation, dispatch, persistence and assertions remain unchanged.
- Prevention: a deterministic regression invalidates the real fixture connection and requires the original canonical job rows after reconnect. It failed with no such table on the old fixture. Existing retention still requires exactly three expired facts removed and unchanged job/attempt/grant rows; timeout/cancellation cases retain their original budgets.

The post-main run exposed the same lifetime bug in Return Analysis setup: its optional contact observer invalidated the memory connection before rebase read smart_reminder_attempts. The suite reported one setup error after 1,578 cases, then a leaked nested fixture kept the process alive until the 45-minute job deadline. Return setup now registers async cleanup immediately after nested setup succeeds, since unittest does not call asyncTearDown after a later setup failure. Its reconnect regression preserves job/attempt/grant rows; the actual migration test and all SQLite return cases remain unchanged.
